# 平台约定速查

## 怎么用

1. **先看 terminal 返回的首行环境声明**，它告诉你当前环境的真实情况：

   ```
   [SHELL: git-bash | os=win32 | console=cp936 | py_io=utf-8 | fs=utf-8]
              ↑平台       ↑控制台编码      ↑Python输出    ↑文件系统
   ```

   - `console=cp936` → 控制台是 GBK，**直接打印 UTF-8 中文会乱码**
   - `py_io=utf-8` → Python 脚本打印中文没问题
   - `fs=utf-8` → 文件名/路径按 UTF-8 处理

2. **再查本表的对应情形**，照做。

3. **表里没有的情形 → 用 `web_search` 查**，不要凭印象试错。
   反复"写文件→运行→逐字节验证→再对照"会浪费大量轮次（实测一次任务
   18 次调用里 11 次耗在编码试错上）。

## Windows

### 写含中文的 .bat / .cmd

**规则**：二选一，**不要写"UTF-8 但不加 chcp"**（cmd 默认代码页 936，必然乱码）。

| 方案 | 做法 | 适用 |
|---|---|---|
| A（推荐） | 文件写 **UTF-8（无 BOM）**，并在 `@echo off` 后加一行 `chcp 65001 >nul` | 想让文件在任何机器上都能正常显示中文 |
| B | 文件写 **GBK 编码** | 只在本机用、不想改代码页 |

**注意事项**：
- 换行符必须是 **CRLF**（纯 LF 可能让 cmd 解析异常）
- 不要写 UTF-8 BOM（cmd 会把 BOM 当命令的一部分）
- 用 `chcp 65001` 的副作用：它会改掉**当前控制台**的代码页（从已有窗口调用时需要留意）

### 检查一个 .bat 写得对不对

```bash
file xxx.bat          # 期望: "DOS batch file, ... with CRLF line terminators"
head -c 3 xxx.bat | xxd   # BOM 检查: 不应是 efbbbf
```

### 路径

| 环境 | 写法 |
|---|---|
| git-bash | `/d/xxx/yyy` 或 `D:/xxx/yyy` |
| cmd | `D:\xxx\yyy` |
| bat 内部 | `%~dp0` 是本 bat 所在目录（**自带结尾反斜杠**，拼接时注意） |

### 命令差异

- git-bash 里调 cmd 内置命令：`cmd //c "命令"`（**双斜杠**，单斜杠会被 MSYS 转成路径）
- `where` 相当于 Linux 的 `which`

## Linux / macOS

### 编码

- 通常已是 UTF-8，用 `locale` 查看当前设置
- 若 `LANG` 未设（新容器常见），中文可能显示为 `?` —— 设 `LANG=C.UTF-8` 即可
- 写 shell 脚本**不需要** chcp 之类的操作

### 换行符

- shell 脚本用 **LF**（若从 Windows 拷贝过来带 CRLF，会报 `\r: command not found`）
- 转换：`sed -i 's/\r$//' file.sh`

### 路径

- 分隔符是 `/`，没有盘符概念

---

## 通用原则

1. **编码问题先分两层定位**：
   - **文件内容**的编码（写进去的字节）
   - **控制台渲染**的编码（终端怎么把这些字节画出来）

   两层不一致才会乱码。**先确认是哪一层的问题，再修**——别一上来就改文件编码。

2. **`file` 命令是判断文件编码/换行符最快的方式**，比写 Python 脚本逐字节检查快得多。

3. **不确定就查**（`web_search`），比试错省轮次。
