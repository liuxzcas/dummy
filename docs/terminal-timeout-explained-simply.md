# 命令卡死问题：一份讲人话的说明

> 面向：任何能读懂中文的人（不需要编程基础）
> 目的：把"为什么 dummy 执行一条命令会卡死"从最底层讲清楚
> 配套（技术细节）：`docs/terminal-timeout-fix-plan.md`

---

## 第一篇：先弄明白 dummy 是怎么"执行命令"的

### 1.1 dummy 本身不会执行命令

dummy 是一个 AI 助手程序。当它需要查看文件、运行脚本时，它**自己不干活**——它会**请一个"工人"来干**。

在这个 Windows 电脑上，这个"工人"叫 **bash**（读作"巴什"，是 Git 附带的一个命令行工具）。

整个流程是这样的：

```
1. dummy 想执行"列出目录"这条命令
2. dummy 找到 bash 这个工人,把命令交给它
3. bash 干活,把结果（文字）写到一个"管道"里
4. dummy 从管道里读结果
5. dummy 把结果拿给 AI 看
```

### 1.2 关键概念："管道"

**管道**是什么？你可以把它想成**一根水管**。

- bash 干活时，把要输出的文字**从管子一头灌进去**
- dummy 在**另一头接水**

**这里有一个极其重要的规则**：

> **dummy 必须等到管子的这一头"彻底没有水了"，才能收工。**

这个规则不是 dummy 自己定的，是 Python（dummy 用的编程语言）内部的规定。它的道理是：如果不等水流完就收工，可能会丢掉后半段结果。

**记住这条规则**——后面所有的麻烦都是它引起的。

### 1.3 还有一个概念："子进程"

bash 接到命令后，**它自己不一定亲自干**。它常常**再找一个小工**来干：

```
dummy
  └─ bash（工人）
       └─ find（小工，真正去搜索文件的程序）
```

**为什么要知道这个**？因为**"工人"和"小工"是两个独立的程序**。你把工人辞退了，小工可能还在干活——**这是本问题的核心**。

## 第二篇：dummy 本来设了"闹钟"，但它不管用

### 2.1 本来应该发生什么

写程序的人知道"有些命令可能跑很久"，所以设了一个**闹钟**：

```
把命令交给 bash 时,顺便说一句：
  "如果 30 秒还没干完,就别干了"
```

这句话在代码里就是一个参数：`timeout=30`。

### 2.2 实际上发生了什么

**闹钟确实响了**——但**响完之后，麻烦才刚开始**。

用一件极简单的事可以证明。我让 bash 执行一条"睡 20 秒"的命令，同时设 5 秒闹钟：

```
预期：5 秒后停止
实际：20.4 秒后才真正返回     ← 实测结果
```

**为什么晚了 4 倍？** 下面是完整过程，一步一步看：

```
第 1 步：5 秒到，闹钟响
        ↓
第 2 步：程序去"辞退工人"——它杀掉了 bash
        ↓
第 3 步：但小工（sleep，就是那个"睡 20 秒"的程序）还在睡！
        ↓
第 4 步：程序转过头去收水（读管道）
        ↓
第 5 步：水管里还有水,因为小工还活着、还攥着管子
        ↓
第 6 步：程序只能干等 —— 等小工自己醒来、松手
        ↓
第 7 步：小工睡够 20 秒,松手 → 程序这才收到水 → 返回
```

**所以"闹钟不管用"这个说法不准确**。准确的说法是：

> **闹钟响了，但它只辞退了工人，没辞退小工；而程序必须等小工松手才能收工。**

### 2.3 所以你遇到的情况是

你让 dummy 执行的那条命令是：

```
find /c/Users /d/ -iname "*.vmx" ...
```

这条命令要**搜索 C 盘和 D 盘的每一个文件夹**，找一种叫 `.vmx` 的文件。

**实测结果**：

| 情况 | 耗时 |
|---|---|
| 刚搜过、系统记住了索引 | **0.3 秒** |
| 第一次搜、要从磁盘一点点读 | **超过 60 秒还没结束** |

**同一个命令，耗时能从 0.3 秒到一分钟以上**——差别在于"系统有没有记住上次的结果"。

**所以超时的时间是"30 秒 + 小工跑完的时间"**。你以为 30 秒后会返回，实际可能是几分钟（甚至更久，取决于要搜多久）。

### 2.4 一个更糟的后果：小工没人管了

闹钟响过、程序返回之后，**那个 `find` 小工还在后台继续搜索**。

它会：

- 继续占用磁盘（你能听到硬盘响）
- 继续占用一点 CPU
- **一直跑到自己搜完为止**

**它变成了一个"没人管的野进程"。**

## 第三篇：为什么"手动中止"之后什么都没留下

### 3.1 你看到的现象

你说：手动中止后没有留下 log 信息。

### 3.2 一步一步还原当时发生的事

```
1. dummy 把命令交给 bash,开始等结果
2. find 在拼命搜索磁盘（很慢）
3. 30 秒到了,闹钟响 → 但按第二篇说的,程序还在等小工松手
4. **在这段等待里,你按了中止**
5. 程序在这里收到"中止"信号
6. 但此时它手里还什么都没有——命令的结果还没读到
7. 程序走"退出流程":保存一下会话记录,然后退出
8. 会话记录里,这条命令的结果是**空的**
9. 于是系统补了一句话:"[工具结果缺失:该次调用未执行或被中断]"
```

**第 9 步那句占位文本,就是你看到的"没有 log"** —— 它不是"没记录"，而是**记录的内容毫无信息量**：

- 它没说你当时在执行**哪条命令**
- 它没说卡了**多久**
- 它没说命令**跑到哪一步**了

**所以真正的问题是"卡住期间，磁盘上没有任何东西能说明它卡在哪"。**

### 3.3 还有一处信息被丢掉了

即使闹钟正常响了（没被手动中止），程序手里其实**已经拿到了一部分结果**——比如 `find` 在超时前已经找到的几个文件。

**但旧代码没有去取这部分结果**，它直接返回了一句固定的话：

```
"[错误] 命令执行超时（30 秒上限）：<命令>"
```

**也就是说：能找到的线索被扔了。**

## 第四篇：怎么修

### 4.1 修法一：辞退工人时，把他的小工一起辞退

**问题**：现在只辞退了 bash，小工还活着。

**修法**：Windows 系统提供了一个命令，叫 `taskkill`，加上一个 `/T` 参数（T 是 Tree，树的意思），意思是**"把这个进程以及它下面雇的所有人，全部辞退"**。

**但这个修法能不能用，我不能靠猜**——我先做实验验证。

### 4.2 实验：真的能辞退干净吗？

**实验做法**：我让 bash 干一件长期活，然后在命令行里打上**一个独一无二的标记**（像贴个编号），这样我就能准确认出"哪些进程是这次实验产生的"，不会和其他程序搞混。

**实验结果**：

```
启动后,带标记的进程有:
  bash.exe  (编号 36508) ← 我请的工人
  bash.exe  (编号 24100) ← ★ 意外发现:工人自己又请了个工人

下命令辞退(杀整棵树):
  成功: 24100 已经辞退（它是 36508 的下属）
  成功: 36508 已经辞退

辞退之后再等结果:
  ★ 0.0 秒就返回了     ← 之前要等 20 秒
```

**结论：这个修法有效。**

**而且实验暴露了一个之前不知道的事**：**bash 会自己再雇一个 bash**（多一层）。

```
dummy → bash(36508) → bash(24100) → 真正干活的程序
                        ↑ 之前不知道还有这一层
```

**所以必须用 `/T`（整棵树）**，只辞退直接请的那个是不够的。

### 4.3 修法二：把已经拿到的结果留下来

**问题**：超时时，已经产生的那部分结果被扔了。

**修法**：超时时**先把管子里的水收一收**，再辞退工人。

**效果**：（示意）原来你会看到

```
[错误] 命令执行超时（30 秒上限）：find /c/Users ...
```

修完变成

```
[SHELL: git-bash | ...]
/Users/xlinz/VM/win10.vmx          ← 超时前已经找到的
/Users/xlinz/VM/ubuntu.vmx         ← 这些被保留下来了
[超时] 命令在 30 秒内没有结束，已被终止（连同它启动的子进程）。
      上面是终止前已经产生的输出（可能为空）。
      如果这是一条需要长时间运行的命令（例如在大目录树里搜索），
      可以考虑缩小范围、或改用更快的查找方式。
```

**注意最后那句的措辞**：它说的是"**可以考虑**"，不是"**你必须**"。

这是这个项目的一条原则：**告诉 AI 发生了什么、有什么选择，但不替它做决定**。

### 4.4 修法三：卡住之前先留个记号

**问题**：卡住期间，磁盘上什么都没有。

**修法**：**在开始执行之前，先写一句"我要开始跑这条命令了"**。

这样即使卡死、即使被手动中止，事后翻记录也能看到：

```
[执行中] 正在运行: find /c/Users /d/ -iname "*.vmx" ...（上限 30 秒）
```

**这样做有两种方式**（需要你选）：

| 方式 | 意思 | 好处 | 代价 |
|---|---|---|---|
| **甲** | 把"执行中"这句话写进**对话历史** | AI 也能看到（下次它就知道"我上次卡在这条命令上"） | 要改一下记录机制（先写"执行中"，拿到结果后再替换掉） |
| **乙** | 只写进**日志文件**（不进对话） | 改动小，不碰对话结构 | AI 看不到，只有你翻日志时能看到 |

### 4.5 修法四：给 shell 的路径加个说明

这是**顺手发现的一个隐患**，不是你的问题引起的，但值得防。

**背景**：dummy 找 bash 时，用的是**完整路径**：

```
C:\Program Files\Git\bin\bash.exe
```

**如果它偷懒**，只写"bash"（让系统自己去找），会发生什么？**我做实验，结果是这样**：

```
系统说"bash 在这里"：C:\Users\xlinz\AppData\Local\hermes\git\usr\bin\bash.EXE
                        ↑ 找到了 Hermes 自带的那个 git

但实际一执行,报错：
  "WSL (25 - Relay) ERROR: execvpe(/bin/bash) failed: No such file or directory"
  ↑ Windows 的 WSL(另一个 Linux 子系统)抢走了这个命令,然后在它自己那里找不到 bash
```

**翻译**：如果写"bash"而不写完整路径，**Windows 可能会把它交给 WSL**，而 WSL 里的 bash 是坏的（这也是你之前记录过的坑）。

**dummy 现在写的是完整路径，所以没这个问题——这是它做对的地方。**

**修法**：在那个位置**加一段注释**，说明"为什么必须写完整路径"。这样将来有人想简化它，会先看到这个说明。

## 第五篇：改完会发生什么

### 5.1 你遇到的那条命令

改之前：

```
输入: find /c/Users /d/ -iname "*.vmx" ...
现象: 卡死,等很久不返回,手动中止后没有任何有用信息
```

改之后：

| 项 | 变化 |
|---|---|
| 返回时间 | **30 秒左右**（不再取决于小工要跑多久） |
| 返回内容 | 含 `[超时]` 说明 + **超时前已经找到的那部分结果** |
| 后台 | **没有野进程残留**（小工也被辞退了） |
| 记录 | 有"我在执行这条命令"的痕迹（取决于 4.4 选甲还是乙） |

### 5.2 正常命令完全不受影响

**这一点要说清楚**：改的是"出事时的处理方式"，**正常执行的那些命令，行为一个字都不变**。

会专门写测试来保证这一点（跑一条普通命令，验证输出、退出状态都和以前一样）。

## 第六篇：顺带说清一个容易误解的地方

**你可能会想**：既然超时这么麻烦，为什么不干脆**让 `find` 跑快点**？

**答案是**：**那不是这个程序该管的事**。

道理是这样的：

```
dummy 的职责:  "把命令交给系统执行,把结果拿回来"
              "如果卡住了,要能中止掉,并且把情况说清楚"

不是它的职责:  "保证每条命令都跑得快"
```

**那"这条命令太慢了"该谁说**？

**该 AI 自己判断** —— 而这正是"把超时前的结果和超时说明给它看"的意义所在：

```
AI 看到:  [超时] ... 上面是终止前已经产生的输出
         /Users/xlinz/VM/win10.vmx

AI 会想:  哦,扫了整个 C 盘和 D 盘,太慢了
         我下次只扫用户目录就够了
```

**换句话说**：修好超时机制之后，**"这条命令太慢"这个问题就变成 AI 能自己发现并改进的事了**——这正是我们一直在做的事（**提供事实，让它判断**）。

## 第七篇：这次修的东西，本质是什么

抛开技术细节，这件事的本质是**三个不同层面的问题**：

| 层面 | 问题 | 性质 |
|---|---|---|
| **第一层** | 闹钟响了，但只辞退了工人，没辞退小工 | **机制不完整** |
| **第二层** | 已经拿到的一部分结果被扔了 | **信息被浪费** |
| **第三层** | 卡住期间什么都不记 | **缺少痕迹** |

**三层都是"原本可以做对，但没做"**——不是设计理念的问题，是**实现上的疏漏**。

**这和之前推翻"验证门"那件事性质完全不同**：

```
验证门那件事: 设计前提错了(想用硬规则替 AI 判断) → 要推翻重来
这次这件事:   设计没问题,是实现没做全     → 补上就行
```

## 附：本文用到的所有实验记录

### 实验 1：那条命令到底有多慢

```
$ time find /c/Users /d/ -iname "*.vmx" -not -path "*/Windows/*" | head -20
real    1m0.053s      ← 跑满 60 秒未结束
user    0m0.015s      ← CPU 几乎没动(说明时间全花在等磁盘)
sys     0m0.136s
```

**另一次（缓存已热）**：0.3 秒。

### 实验 2：闹钟为什么不精确

```
设定 5 秒,执行"睡 20 秒"：
  → TimeoutExpired 在 20.4 秒触发
  → 多等了 15.4 秒
```

### 实验 3：小工确实会变成野进程

```
设 5 秒闹钟,执行"睡 20 秒"
  → 闹钟 5.0 秒正常触发
  → 但结束后检查:sleep 进程存活 1 个   ← 泄漏
```

### 实验 4：辞退整棵树有效

```
带唯一标记启动:
  bash.exe (36508) ← 工人
  bash.exe (24100) ← 工人自己请的工人

taskkill /F /T /PID 36508:
  SUCCESS: 24100 (child) terminated
  SUCCESS: 36508 terminated
  → 之后 0.0 秒就拿到结果了
```
