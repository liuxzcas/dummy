# dummy 跨组件冲突审计（2026-09-15）

## 0. 为什么做这次审计

起点是一个具体怀疑：**对话压缩器（Phase 2.2）会与最近新增的组件冲突**。
压缩器是唯一会**整体重写 `self.history`** 的组件，而新增的三件套（P1a 护栏、
P1b 收尾验证门、P2b 历史卫生）都依赖历史与"按轮状态"。两者假设不一致就会出鬼。

审计目标不是"找出所有 bug"，而是回答一个可证伪的问题：**这些组件之间的假设有
没有互相矛盾的地方？**

## 1. 方法

两条腿，缺一不可：

**静态**：先把"谁在读 `self.history`"穷举出来（`core.py` 里 30 处），逐个核对其
假设是否与压缩器重写后的形态相容。

**动态**：静态只能发现"读代码看得出的矛盾"；计数类判据必须跑。用假 LLM 驱动
真实工具循环（`tests/conftest.py` 的 `ScriptedLLM`）写 4 个探针，让冲突表现为
**可观测的行为差异**，而不是"我觉得会冲突"。

原则：**结论必须有可复现实验或精确定位，不接受推测。**

## 2. 确认的冲突

### ① 护栏 ↔ 验证门：互锁（最严重）

**机制**：护栏的 `exact_failure` 只比对 **工具名 + 参数**，不看报错内容。而
"改一处 → 跑一次测试"产生的是同命令、**不同报错** —— 这不是原地打转，却被计数。

**实测**（改了 `.py` 后连跑 6 次全量测试，每次失败原因都不同）：

```
测试真实执行次数 : 5
护栏拦截次数     : 1        ← 第 6 次被拦
验证门驳回次数   : 2
是否留下通过证据 : 否
返回值           : '我改好了。'     ← 无证据却声称完成
```

**互锁**：护栏禁止再执行那条命令，验证门却要求"该命令通过才算证据"——模型
**无法同时满足**，最终以"无证据 + 声称完成"收尾，恰好是验证门要防的事。

**性质**：P1a 引入的。Hermes 有同样的判据，但它的 `hard_stop` **默认关**（只告警）；
dummy 默认**开启**，把"无害的告警"变成了"硬拦截"。

### ② 合成 user 消息 ↔ 压缩器：挤占"保留最近 N 轮"名额

**机制**：压缩器按**所有 `role="user"` 消息**数决定 L2 切点。而新加的三种合成消息
都是 user 角色：打断提示词、验证门驳回（每轮最多 2 条）、轮次用尽指令。

**实测**：

```
合成消息 0 条 → 保留真实对话 6 轮
合成消息 2 条 → 保留真实对话 4 轮
合成消息 4 条 → 保留真实对话 2 轮
```

**后果**：触发过 2 次驳回的轮次，直接吃掉 2 个名额，真实对话被**提前摘要掉**，
`recent_turns_keep = 6` 的承诺名不副实。

### ③ L1 折叠标记 ↔ 缺失的检索工具：悬空承诺

**机制**：折叠后的标记写着"完整内容可查询归档表 `tool_result_archive(tool_call_id=...)`"
（`compressor.py`）。归档表与读取 SQL 都存在（`session_store.py` 建表 + 查询），
但**没有任何注册工具**——项目只注册 terminal / read_file / write_file /
web_search / web_extract。

**准确说法**：模型**能**用 terminal 直接 `sqlite3 session.db ...` 捞回来（所以不是
"信息永久丢失"），但标记里那个"函数式"的调用形式**不存在**，模型可能去调一个不存在
的工具然后放弃。属**接口与承诺不一致**。

### ④ 验证门 ↔ 用户取消：轻微（未改）

按 `n` 取消 pytest → 不留证据（正确）→ 门接着驳回"没有证据"，等于让模型去做
用户刚拒绝的事。有出口（"说明具体卡点"）且上限 2 次，是**轻微烦人**而非死锁。

## 3. 排除的怀疑（同样是审计结果）

| 怀疑点 | 结论 | 依据 |
|---|---|---|
| L1 折叠会破坏"无进展"判定 | ❌ 不成立 | 护栏与验证门都对**实时工具结果**取哈希/记账，**不读历史副本**；折叠只改历史里的 `content` |
| 压缩 ↔ system prompt 注入器（会单向膨胀？） | ❌ 不成立 | 三个注入器都**幂等**（`当前时间:` / `当前工作目录:` / `## 可用技能` 先删旧段再写），且只在 `chat()` 开头跑一次；压缩器的 `system_msgs` 完整保留非压缩 system 消息 → `history[0]` 始终是 system prompt |
| `_validate_history` ↔ P2b 删悬空尾 | ❌ 一致 | 压缩器校验也要求"结尾不允许未响应的 `tool_calls`"，与 `repair_tool_pairing` 同一规则 |
| `close_interrupted_tool_sequence` ↔ 压缩 L2 切点 | ❌ 安全 | 切点在 **user 边界**，合成 assistant 不可能成为切点起点 |
| 被拦调用不记账 ↔ 工具错误率统计 | ❌ 无污染 | 拦截走 `else` 分支不调 dispatch → `stat["calls"]` 不增 |

**最关键的一条**：用户怀疑的"压缩重写历史 ↔ 新增组件的按轮状态"答案是
**不冲突**——因为护栏和验证门的状态**全部来自实时数据**（工具结果、参数、序号），
压缩重写的是历史副本，两者不共享状态。真正被压缩影响的只有 ② 那个名额问题。

## 4. 修法

| 修 | 内容 | 位置 |
|---|---|---|
| ① | `exact_failure` 的计数**要求失败内容也相同**（记 `(结果哈希, 次数)`，哈希变了重新计数）。与只读工具的 `no_progress` 用同一种"指纹+次数"形状 | `tool_guardrails.py` |
| ② | 合成 user 消息打 `_meta.synthetic`，压缩器**只数真实 user 轮次** | `core.py` / `compressor.py` |
| ③ | 折叠标记改为**可执行的取回办法**（表名 + 键 + `sqlite3` 命令），不再写成函数调用 | `compressor.py` |
| ④ | 验证门：取证命令被护栏拦掉时记为**被阻断**，不再驳回（区分"模型偷懒"与"模型被挡住"） | `verify_stop.py` / `core.py` |

设计取舍说明：

- ① 让 dummy 的判据**比 Hermes 更严**（多要求"报错也相同"）。理由：Hermes 只告警，
  dummy 硬停，代价不同则判据不必相同。真循环（同命令同报错 5 次）仍会被拦。
- ④ 保留一个已知的可绕性：模型可以故意重复失败让护栏阻断取证，从而跳过验证门。
  **不做防御**——本地单用户交互场景没有对手；伪造验证远比这省事。
- ③ 选**改措辞**而非新增只读工具：模型有 terminal，取回能力已经具备；新增工具会让
  每次请求多一份工具定义（永久 token 成本）。

## 6. 事故记录：一次测试误写炸出 101 个进程

**经过**：给 ① 写第一版 e2e 时用了 `run_script` 夹具——它内部**会立刻真跑一遍工具**。
脚本里 5 次 `terminal("python -m pytest tests/ -q")` 于是**真的跑了 5 遍完整套件**；
而套件里又有会真跑 pytest 的测试 → **递归套娃**，累积出 **101 个 `python -m pytest`
进程（约 9GB）**，把系统资源耗尽。

**症状**：`bash: dofork: ... errno 11`（EAGAIN，无法 fork）、`[WinError 1455] 分页文件太小`，
连**无关的**测试都开始失败（`test_e2e_verified_edit_passes` 因嵌套 bash 起不来而无证据 → 门驳回）。
**这类失败极具误导性**——看起来像代码 bug，实际是资源枯竭。清理滞留进程后全套立刻恢复绿色。

**防呆**：`tests/conftest.py` 的 `run_script` 现在会**扫描脚本**，发现让 terminal 真跑
pytest（且不带 `--collect-only`）就立即 `AssertionError`，并提示正确写法。

**教训**：夹具"会真跑"这一点必须是显式的——隐式的副作用（跑真命令）在测试里等同于
不可控的资源消耗。

## 7. 已知局限

- ① 的"失败内容相同"用结果哈希判定：命令输出里含**时间戳/随机数**时，同一份失败每次
  哈希都不同，护栏会**永不触发**。对"稳定复现的失败"无损，对"每次输出都带抖动"的
  失败会漏判。选择偏保守（宁可漏判，不可误拦）。
- ④ 可绕（见 §4）。
- 本次审计覆盖"组件间的假设矛盾"，**不覆盖**各组件自身的实现 bug。
