# 历史层架构方案对照实验 — 结论

日期:2026-09-16 | 分支:`arch/history-settle` / `arch/history-projected` / `arch/history-atomic`

## 0. 一句话结论

**路线 5(原子批次)胜出**:唯一同时通过硬标准与软标准的方案(208 全绿),
且改动最小(只挪 2 处落库时机,不新增任何兜底)。
**路线 2(投影器)是它的互补件**,不是竞争项——一个管落库侧,一个管发送侧。

## 1. 问题的重新认识(实验过程中修正了三次)

最初的目标是"把 5~7 处兜底收敛掉",过程中对问题本身的认识被纠正了三次:

| 阶段 | 当时的认识 | 被什么推翻 |
|---|---|---|
| 起 | "危险时刻"的入口很多(异常/Ctrl+C/强杀/断电) | 探针实测:经 chat 的异常路径**已被现有机制兜住** |
| 中 | 问题在于"什么时候修最合适" | 探针实测:**磁盘上真的躺过半个批次**(main 分支 4 条历史,结尾悬空) |
| 终 | **问题在于"非法状态被允许落库"** | `_persist_history()` 在每条 tool 结果后都调 —— 非法状态是**被主动写进磁盘的** |

**根因陈述**:`assistant(tool_calls)` 与"同批全部 tool 回复"之间有一个时间窗,
旧实现在这个窗口内就落库了。能让进程停在该窗口的原因(异常/强杀/断电)只是
"谁来触发",不是根因;根因是**窗口被暴露给了磁盘**。

## 2. 判据的三次校正(方法论记录)

判据本身就是实验的主要产出之一,它的三次校正值得单独记:

| 版本 | 问题 | 校正 |
|---|---|---|
| v1 | 只有 AR1(直接 `save→load`) | 它绕开 `chat()`,对"收口类"方案无从判定 → 拆出 AR-chat |
| v2 | AR-store 被当作验收标准 | 真实系统里历史**唯一写入者是 chat()**,"外部直接 save"是假问题 → 降为参考项,新增 AR-stop |
| v3 | 只看"停机后最终状态" | 无法区分"事后修"与"不让发生" → 新增 SOFT1(落库快照探针) |

**教训**:判据测错对象比没有判据更危险 —— 它会让"没解决问题"看起来像"通过"。
本实验里 v2 的错判差点让路线 5 的收益被埋没。

## 3. 对照表

| | AR-stop1(硬) | SOFT1(软) | 全套 | 兜底点 | 改动 |
|---|---|---|---|---|---|
| **main** | ❌ 红 | ❌ xfail | 202/3 | 7 | — |
| **路线 3** 收口 | ✅ 绿 | ❌ xfail | 202/3 | 7→8 | chat 拆两函数 + main 删一函数 |
| **路线 2** 投影 | ❌ 红 | ❌ xfail | 206/1 | 7→**5** | 新增投影器 + 删两处保险丝 |
| **路线 5** 原子批次 | ✅ **绿** | ✅ **通过** | **208/0** | 7 | 挪 2 处落库时机 |

软标准(SOFT1)判法:给 `save_history` 装探针,记录**每一次落库快照**;
停机场景跑完后检查每个快照是否合法。通过 = 磁盘上从未出现非法状态。

## 4. 三条路线各自的价值

### 路线 5 原子批次 —— 采纳
把"`assistant(tool_calls)` + 同批全部 tool 回复"当作**一个原子写**,批次收尾
才落库。非法状态**从未被写进磁盘**,所以不需要事后修。

- 通过硬标准(停机后磁盘合法)且通过软标准(每一次落库快照都合法)
- **不依赖任何收尾动作**:kill -9 / 断电 / 任务管理器结束进程都不影响
- 改动最小:删一处落库、加一处落库

### 路线 2 投影器 —— 采纳为互补件
`project_messages()` 纯函数保证"发出去的 messages 永远合法"。

- 它**修不了** AR-stop1(没碰落库时机),所以不是替代方案
- 但它的价值独立成立:把发送侧不变量收在**一个函数**里,并可**删掉两处保险丝**
  (实测零回归)——兜底点 7→5
- 与项目已有三单点同构:`_parse_tool_arguments` / `_make_confirm` / `_append_user_turn`

### 路线 3 单点收口 —— 封存
`chat()` 的 `finally` 统一收口。通过硬标准但**不通过软标准**。

- 它是"事后修"的天花板:修得足够及时,用户可见行为与路线 5 等价
- 但依赖"进程能走到 finally";强杀时磁盘上留着半个批次
- 按用户定的口径(**软标准通过加分、不通过也可采纳**),它可采纳但不如路线 5
- 保留为对照证据:它证明了"收口类方案到不了落库侧"

## 5. 未采纳的方向及理由

| 方向 | 未采纳理由 |
|---|---|
| **受管 History 类**(写入时保证) | 已用 T4 形态证明"写的时候不知道后面还有没有半个循环"——`_append_user_turn` 就是活例子(修了角色交替、漏了配对)。有先天缺陷 |
| **落库不变式**(save 前校验) | 破坏"持久层忠实读取"的对称性;且验证成本高(每次落库都要校验全量历史) |
| **快照回滚**(Hermes 做法) | 过重:dummy 场景不需要回滚副作用,只需保证历史合法 |
| **事件溯源**(append-only + 投影) | 与路线 2 高度重叠,但重构代价大得多 |

## 6. 建议的落地组合

```
路线 5(原子批次)   ← 主方案,解决"磁盘上不进非法状态"
   +
路线 2(投影器)     ← 互补,解决"发出去的永远合法"并收敛兜底点
```

两者**不冲突**:一个管写入侧的落库时机,一个管读取侧的发送投影。
合并后的预期:AR 全绿 + SOFT1 通过 + 兜底点 7→5。
