## 一、这份文档要回答什么

2026-09-15 ~ 2026-09-18 这四天里,dummy 上线了两个"安全机制",然后又**全部推翻**：

| 机制 | 上线 | 推翻 |
|---|---|---|
| **工具护栏**（P1a） | `d4f9e40`：检测到"同一失败反复出现"就**拦截**该调用 | `d743aed`：改为**纯观察者,零拦截** |
| **收尾验证门**（P1b） | `11e0512`：模型想收尾但拿不出"全量测试通过"证据就**驳回**（上限 2 次） | `a02d0c5`：改为**情况说明**；`7dac807`：删除整个模块 |

**这两次推翻不是"发现 bug 然后修 bug"**——两个机制都按设计正常工作,没有实现缺陷。

**它们是"设计前提本身错了"。**

这份复盘记录三件事：
1. 当时**为什么**认为这两个机制是必要的（决策依据是什么）
2. 实测数据**如何一步步否定**这些依据
3. 推翻之后,项目确立了什么**更根本的原则**

## 二、S — 情境（Situation）

### 2.1 起点：两个真实事故

`docs/p1b-verification-design.md` 第 0 节记录了促使上这两道门的事故：

| 事故 | 现象 |
|---|---|
| 雷战机那次 | LLM 改完黑屏,说"修好了",实际根本没验证运行,打开还是黑屏 |
| 网页/PPT 那次 | 文件写出来了、语法没错,但跑不起来,来回返工 |

当时的根因判断（原文）：

> 根因不是模型"不会写代码",而是**框架允许它自己说"我完成了"**。

**这个判断导出了一个设计目标**：框架应当**阻止**模型"没验证就宣布完成"。

### 2.2 另一个起点：Hermes 的现成参照

dummy 当时正在系统性地对照 Hermes 的实现（见 `docs/hermes-vs-dummy-tool-loop.md`）。Hermes 有两套机制：

| Hermes 机制 | 位置 | 行为 |
|---|---|---|
| `tool_guardrails.py` | `agent/` | 检测重复调用,可**拦截**（默认关闭） |
| `verification_stop.py` | `agent/` | 收尾时要求验证证据 |

**照搬这两个机制是一个自然而然的选择。**

### 2.3 当时的决策（有完整原话记录）

**护栏的决策注释**（`d4f9e40` 版本,现已删除）：

```python
默认策略（dummy 有意偏离 Hermes 之处，需要时改回即可）：
- Hermes 默认 hard_stop_enabled=False（多端产品，怕拦截破坏自动化流程）
- dummy 默认 **True**：单用户交互式，且目标就是止损省轮次。
  想退化成"只告警不拦截"：设 DUMMY_GUARDRAIL_HARD_STOP=0
```

**这段注释的三个信息**：
1. 作者**知道** Hermes 默认关闭拦截
2. 作者**有意**选择默认开启
3. 理由是"**单用户交互式 + 目标就是止损省轮次**"

**验证门的决策**（`docs/p1b-verification-design.md` 第 6 节）：调研了 6 个实现 + 4 篇论文,选定"**档 A**"——证据 = 一次**完整测试套件**的 pytest 成功执行（全量、晚于最后一次编辑、留痕）。

### 2.4 当时的调研结论（不是拍脑袋）

`p1b-verification-design.md` 有一节专门回答"多严才算严",结论是：

> 只谈"严"会把设计带偏（典型误区：把阈值从 5 调到 2,那只是更烦,不是更严）。

然后把它拆成**三个独立的轴**：

| 轴 | 内容 |
|---|---|
| 证据 | 什么算证据 |
| 判决者 | 谁来判断 |
| 强制 | 判决之后怎么办 |

并给出**学术依据**：

> Huang et al. 2024（arXiv:2310.01798）指出无外部反馈的自纠效果更差；
> CRITIC（arXiv:2305.11738）指出 critique 必须锚定外部工具。

**当时最深的一条结论**（原文）：

> 六家的"严"没有一家靠"更聪明的评委",**全是把判决外包给退出码**。

**所以当时的方案在逻辑上是自洽的**：既然业界都靠退出码,那 dummy 也用退出码;既然 Hermes 有这套机制,那 dummy 也照搬。

## 三、T — 任务（Task）

上线这两个机制,并让它们真正起作用。

**P1a 护栏的具体目标**：
- 防止 Agent 在同一个地方反复空转、白烧 token 和轮次
- 两个信号：① 完全相同失败（工具 + 参数 + 失败内容三者都相同）② 只读调用无进展（结果与上次完全相同）
- 阈值：第 2 次告警 / 第 6 次拦截

**P1b 验证门的具体目标**：
- 模型想收尾时,如果本轮改过代码类文件却拿不出"全量测试通过"的证据 → **驳回**
- 驳回上限 2 次（防死循环）
- 驳回文案带出口（"无法验证就说明具体卡点,不要声称已完成"）

**两者的设计哲学是同一个**：

> 用**硬规则**拦住模型的"不可靠行为"。

## 四、A — 行动（Action）：机制上线,然后被数据否定

### 4.1 第一次异常：验证门与护栏**互锁**

上线 P1a 之后,出现了一个当时没预料到的组合：

```
护栏的逻辑:同工具+同参数+同失败内容 连续 6 次 → 拦截
验证门的逻辑:本轮改过代码类文件 → 必须有"全量 pytest 通过"的证据

场景:
  1. 模型改了代码
  2. 模型想收尾 → 验证门要求它跑 pytest
  3. 模型跑 pytest → 失败了（因为改动有 bug）
  4. 模型再跑 → 还是同样的失败（因为没改代码就重跑）
  5. 护栏检测到"同一份失败连续 6 次" → **拦截,不允许再跑**
  6. 但验证门仍然要求"必须有 pytest 通过的证据"
  → **互锁：门要求跑、护栏禁止跑**
```

**这个互锁是第一次提示"两个硬规则会互相冲突"**。当时的处理是"取证命令被拦时门放行"（后来这个补丁也随验证门一起删除了）。

**但此时还没有否定设计本身** —— 只是发现了两个机制之间的协调问题。

### 4.2 第二次异常：一次真实任务的代价

一份真实对话记录（用户提供的 `conversation_20260916_160913.json`）暴露了完整代价。任务本身很简单：

> "给自己创建一个启动器"（Windows 下用 Windows Terminal 运行 main.py）

**实测统计数据**：

```
消息数: 134 条
工具调用: 66 次
用户输入: 7 条 —— 其中 5 条是系统合成的:
  [54]  验证门驳回
  [88]  验证门驳回
  [93]  轮次用尽强制收尾
  [125] 验证门驳回
  [130] 验证门驳回        ← 4 次驳回!上限明明是 2

真实用于"创建启动器"的只有 ~13 次调用
其余 ~53 次(80%)消耗在验证门连锁反应 + 环境探测上
```

**三个问题同时出现**：

**问题 1：驳回上限"每轮 2 次"被用户插话重置**

```
代码: self.turns... build_stop_nudge 检查 self._attempts >= self.max_attempts
      core.py 在 chat 开头调 reset_for_turn() 清零

对话记录:
  [54] 驳回（第 1 轮）
  [88] 驳回（第 1 轮，到上限）
  ↓ 用户在第 95 条说了话 → 开新轮 → reset_for_turn() 清零
  [125] 驳回（第 2 轮，重新计数）
  [130] 驳回（第 2 轮，到上限）
  → 共 4 次
```

**问题 2：`.bat` 文件被当成"需要全量测试证据"的代码产物**

```
验证门的 is_verifiable_path() 是【黑名单式豁免】:
  放行: .md .markdown .mdx .rst .txt .adoc .log .csv .tsv + LICENSE/CHANGELOG
  其余: 一律要求"全量 pytest 通过"的证据

.bat 不在白名单 → 模型被迫为"创建一个批处理启动器"提供 pytest 证据
→ 实测它跑了 ~8 次全量 pytest（而那证明不了任何事）
```

**问题 3：门只认一种证据形态**

模型尝试过的**有效验证**全不被认：

| 模型做的 | 是否被认作证据 |
|---|---|
| 写 `drill.ps1` 测试脚本 | ❌ |
| `drillA.bat` / `drillB.bat` 对照实验 | ❌ |
| `lfcheck.py` 检查换行符 | ❌ |
| `fix_verify.py` 验证修复 | ❌ |
| 跑全量 pytest | ✅ **唯一被认的**（而那恰恰证明不了这个 bat 能不能跑） |

**最终以"轮次用尽强制收尾"结束**（`[93]`）。

**因果链**：

```
问题 2（bat 被要求 pytest）→ 逻辑上无法满足
    ↓
问题 3（有效验证不被认）→ 只能反复跑 pytest
    ↓
烧光轮次（40 轮上限用尽）
问题 1（上限按轮清零）独立也导致烧轮次
两个同时出现 → 消耗被放大
```

### 4.3 转折点：用户的方向性指正

看到上述数据后,用户的判断是：

> "我认为有些东西方向错了。我们关于'任务完成了吗？''执行对了吗？''什么算证据？'之类问题的判断回答，现在是靠一条一条写死的硬规则。我认为这与最开始的方向相悖。
>
> 我们应该发挥 LLM 的优势，让 LLM 来选取自己需要的东西，分析并得出结论，而 agent 要做的是提供运行过程中产生的相关信息（然后比如通过放进上下文里）给到 LLM，而不是代替 LLM 去做判断。"

**这段话是整件事的转折点。** 它把问题从"验证门有 3 个 bug"提升到"**用硬规则做语义判断这件事本身错了**"。

**作者当时的回应（承认方向偏了）**：

指出三个 bug 是**同一个病**——

> **规则枚举不完现实**

并回看演进路径：最初 `write_file` 自带语法检查 → 后来加 `verify_stop.py` 一堆硬规则 → 现在 346 行 + 三个 bug。

**然后划清了边界**：

| 类别 | 谁判断 | 现状 |
|---|---|---|
| 协议合法性（配对/角色交替） | 代码硬保证 | ✅ 对的 |
| 安全确认 | 人 | ✅ 对的 |
| **"任务完成了吗 / 对了吗 / 什么算证据"** | **模型** | ❌ **被硬规则劫持了** |

### 4.4 行动一：验证门 → 情况说明（`a02d0c5`）

**删除判决逻辑,改为陈述事实**。

新建 `turn_context.py`（170 行）,在模型想收尾时附一份**情况说明**：

```
[本轮运行情况]
本轮改动/新建的文件:
- E:\...\启动Dummy.bat        (新建)
- C:\...\Temp\lfcheck.py      (临时)
本轮执行记录:
- python -m pytest tests/ -q  → 211 passed, 1 xfailed   [12.4s]
- 启动Dummy.bat 执行了 2 次,均只打开 terminal,未见 main.py 进程
- errlog.txt 有内容(未读) → '…\Git\bin\bash' 不是内部或外部命令
```

**关键差别（用同一场景对比）**：

| | 旧的判决门 | 新的情况说明 |
|---|---|---|
| 模型看到什么 | "你没有验证证据"（判决） | `'…\Git\bin\bash' 不是内部或外部命令`（真实报错） |
| 模型能做什么 | 只能去**满足规则**（跑 pytest） | 能**判断**"bat 里那行路径写错了" |

**实测效果对比**（同一任务）：

| | 判决门 | 情况说明 |
|---|---|---|
| 工具调用 | 66 次 | **4 次** |
| 驳回次数 | 4 | **0** |
| 轮次用尽中断 | 是 | 否 |

**并且那 66 次调用都没做到的事**（发现 bat 路径配错），情况说明**一次就让它看出来了**——因为报错原样摆在它面前。

### 4.5 行动二：护栏从拦截到纯观察者（两次收紧）

**第一次收紧（`20156ed`）：block → pause**

```python
# 旧:第 6 次起【不再执行】该调用,直到轮次用尽
action="block"

# 新:只【拦下这一次】,把事实报告给模型,循环继续
action="pause"
```

**为什么改**：pause 的语义是"拦下这一次",但**它仍然是判决**——模型想跑,护栏说"不行,先停一下"。

**第二次收紧（`d743aed`）：pause → report（零拦截）**

用户的判断是关键：

> "既然每次 LLM 都介入，那就不必拦截了，只需要适时（比如6次完全重复后）添一句简短描述情况的报告就行了，剩下的交给LLM。"

**这个判断建立在一个代码结构事实上**：

```
tool_calling_loop 的结构:
    while True:
        LLM 调用  ←────────────┐
        ↓                      │
        有 tool_calls ?         │
        ├─ 是 → 执行工具        │
        │      → 结果进历史     │
        │      → 回到循环顶 ────┘   ← **模型每次都重新介入**
        └─ 否 → 收尾,退出
```

**每个工具执行完,模型都会看到结果并重新决策**——所以**不需要代码替它按暂停键**。

**改后的护栏**：

```python
# 纯观察者:从不阻止任何调用,只在重复到阈值时往工具结果后追加一句事实
[护栏提示] 你已经连续 5 次执行了同一个调用，结果完全相同：
  · 工具：terminal
  · 参数：{"command": "python -m pytest tests/ -q"}
  · 这期间你没有改动任何文件。
```

**代价**：重复调用会真的执行（浪费一次执行）。**但**：
- 一次工具执行的代价 ≈ 0（本地命令）
- **一次 LLM 调用的代价才是主要的**
- 模型看到报告后**下一轮就会改变行为**

### 4.6 行动三：删除验证门（`7dac807`）

**`verify_stop.py` 346 行 + 30 条测试全部删除。**

删除理由（提交信息原文）：

> 审判角色已于 `a02d0c5` 移交给 `turn_context`（只陈述事实）,`verify_stop` 自此不再被 `core.py` 调用,只剩测试引用它自己。
>
> 为什么必须删而不是留着：**留着会让读代码的人以为它还在工作**（我自己就被误导过一次:以为它有 5 个消费方,实际只剩 2 个）。

```
[第 95 条] 模型说:
  "查完了,结论是:没有。但我要更正一下之前的说法——
   我上一轮只验了 main.py/core.py/ui.py/colors.py 的 diff,
```

**它主动发现了自己上一轮的验证不完整并更正。**

**这是"硬规则"从未带来的行为**——因为硬规则只告诉它"你没证据",不告诉它"该检查什么"。

## 六、经验教训

### 教训一：**"业界都这么做"不等于"该这么做"**

当时的调研是扎实的（6 个实现 + 4 篇论文 + 三个轴的拆解），结论也正确：

> 六家的"严"没有一家靠"更聪明的评委",全是把判决外包给退出码。

**但这条结论只在"判决者轴"上成立** —— 它回答的是"如果要判决,谁判"。

**它没有回答"该不该判决"** —— 而这才是 dummy 真正的问题。

**可操作的检验方法**：调研得到"业界共识"时,要追问一句：**这个共识的前提在我这里成立吗？**

Hermes 的情境是"多端产品,怕拦截破坏自动化流程",dummy 是"单用户交互式"——**情境不同,照搬结论就会错**。

（讽刺的是,当时的注释里**明确写了这个差异**（"dummy 有意偏离 Hermes"）,并据此选择了**更激进**的默认值——而正确结论恰恰相反：正因为是单用户交互,才**更不该**用硬规则挡用户。）

### 教训二：**同一个判断散落在多处,就会一起错**

验证门的三个 bug 表面无关：

| bug | 表面原因 |
|---|---|
| 上限被重置 | `reset_for_turn()` 在 chat 开头清零 |
| `.bat` 被要求 pytest | 豁免名单是黑名单式 |
| 有效验证不被认 | 只认一种证据形态 |

**但根因是同一个**：**"什么算证据"这个语义判断,被拆成了三条独立的硬规则**（豁免名单 / 全局测试命令 / 时效检查）。**任何一条枚举不全,整个机制就失效。**

**这与后来发现的另一个 bug 是同构的**（`llm.chat()` 取值方式,4 处各写各的,一起错）——**说明这是一个反复出现的模式**。

**对策**：收口。一个判断只在一个地方做（`turn_context` 收口了"收尾时提供什么信息";`message_content` 收口了"怎么取内容"）。

### 教训三：**权衡要比"频率 × 单次代价",不能只比"哪种更优雅"**

**背景**：历史层架构选型时,三个方案并行对照,最终在路线 3（单点收口）与路线 5（原子批次）之间选择。

**作者的初步判断**：路线 5 更好,因为它能做到"磁盘上永不出现非法状态"（一种更强的保证）。

**用户推翻了它**：

> "路线3的'正在执行工具时 ctrl+c，能捞回已完成的工具结果'同样很重要。"

**作者承认算错了**：

> 拿罕见事件（强杀/断电）的收益换高频操作（Ctrl+C）的损失,且"重跑一次就好"的前提不成立——**工具未必幂等**。

**正确的比较方式**：

```
不能用: 方案 A 的保证更强 → 选 A
应当用: 频率 × 单次代价
  路线 5 的收益: 罕见事件(强杀/断电)下磁盘永不非法 → 低频 × 代价中
  路线 3 的收益: 高频操作(Ctrl+C)保住已完成结果 → 高频 × 代价高(工具不幂等时)
```

### 教训四：**"止损"的动机是对的,但止损的对象错了**

护栏最初的动机完全正当（"防 Agent 反复空转白烧轮次"）。**问题在于止损的手段**：

```
错的: 拦住模型的调用（它可能确实需要重跑）
对的: 把"你在重复"这个事实告诉它，让它自己决定
```

**后果对比**：

| 手段 | 效果 |
|---|---|
| 拦截 | 模型被迫绕路；且与验证门产生互锁 |
| 报告事实 | 模型下一轮改变行为（它不像人那样"硬要再跑一次"） |

**而且"报告"没有任何代价** —— 追加一句文本,不阻止任何操作。

### 教训五：**实测数据 > 设计推理**

这四个机制/修复的推翻,**没有一个是靠"再想一遍"发现的**,全部来自实测：

| 推翻 | 触发它的数据 |
|---|---|
| 验证门 | 一份真实对话记录：66 次调用 / 4 次驳回 / 5 条系统合成消息 |
| 护栏拦截 | 互锁场景 + "循环每轮都会回到模型"这个代码结构事实 |
| `.bat` 要求 pytest | 实测它跑了 8 次无关的 pytest |
| "有效验证不被认" | 逐条比对它做过什么 vs 门认什么 |

**尤其值得记的是**：验证门的三个 bug 在**代码审查中看不出来**——它们都是"逻辑正确但前提错误"。**只有把真实的调用序列摊开、数一遍,才看得见。**

### 教训六：**"删掉"比"留着"更需要理由**

`verify_stop.py` 删除时,作者的顾虑是：

> 留着会让读代码的人以为它还在工作（我自己就被误导过一次）。

**这句话里有个值得记的细节**：**误导作者本人的,正是"没删的死代码"**。作者在评估它的消费方时,判断它还有 5 个调用点——实际只剩 2 个（且那 2 个也在后来的改动中断了链）。

**推论**：一个不再被调用的模块,**它的存在本身就是误导**。"以后可能用得上"是很弱的理由——**版本控制里本来就有历史**。

## 七、最终确立的原则

这次推翻之后,项目把结论写进了总设计文档 `docs/design-zh.html` **§2「判断的归属：哪些给代码，哪些给模型」**：

### 判据

**问：这个问题是"协议/事实"还是"语义"？**

| 类别 | 谁判断 | 例子 | 为什么 |
|---|---|---|---|
| **协议合法性** | **代码硬保证** | `tool_calls` ↔ `tool` 配对、角色交替 | API 强制,可枚举,无歧义 |
| **安全确认** | **人** | 执行命令前确认、写项目外文件前确认 | 涉及外部影响,需人负责 |
| **语义判断** | **模型** | "任务完成了吗"、"什么算证据"、"这次重复是否合理" | **枚举不完现实** |

### 三条判别的具体检验法

**① 能不能穷举？**
- 能（如"退出码非 0"）→ 可以给代码
- 不能（如"什么算验证过了"）→ 必须给模型

**② 错了有没有代价？**
- 协议错误 → API 直接 400（**硬失败,可见**）→ 可以给代码
- 语义错误 → 静默的错误结论（**软失败,不可见**）→ 给代码就会出验证门那三个 bug

**③ 这个信息模型自己能不能看到？**
- 能看到（工具结果、文件内容）→ 让模型判断
- 看不到（"你重复了 5 次"/"控制台编码是 cp936"）→ **代码负责把事实摆出来**

**第 ③ 条是本项目后来一系列改动的主线**：

| 机制 | 提供什么事实 |
|---|---|
| `tool_guardrails` | "你连续 5 次执行了同一个调用,结果完全相同,这期间你没改动任何文件" |
| `turn_context` | "本轮改了什么、跑了什么、结果长什么样" |
| `env_probe` | "控制台编码是 cp936" |
| `write_file` 返回值 | "[换行 CRLF]" |

**它们形式各异,但语义完全一致**：**不判决,只陈述事实。**
