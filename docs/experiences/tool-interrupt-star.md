# 工具打断功能开发复盘 — STAR 法则总结

> 项目:dummy-agent
> 日期:2026-08-14
> 主题:**前期构思不成熟 → 后期改动牵一发而动全身**的典型工程实践应对

---

## 一、功能背景与开发过程(完整回顾)

### 需求起点

在 tool_calling loop 中加入"随时打断 + 听用户意见":
1. 暂停循环(等当前工具执行完,不再跑下一个 tool call)
2. 用户能在断点输入提示词
3. 提示词作为 user 消息进入下一轮,LLM 重新规划

用户初步想法:`/p xxxx` 行内带提示词。

### 设计演进(五轮收敛)

| 轮 | 方案 | 走向 |
|----|------|------|
| 1 | 工具确认处解析 `/p xxxx` | 用户想法,断点 = 确认处 |
| 2 | 升级"任何时间"打断 | 非阻塞监听(msvcrt 轮询 + 检查点) |
| 3 | 只改 core.py 降耦合 | 确认仍在工具内,代价:确认处 /p 丢失 |
| 4 | 确认统一归 core 管理 | 工具纯函数化,但丢失 write_file diff 细节 |
| 5(定稿) | **确认语义归 handler + /p 拦截归 core** | 注入 `_confirm` 函数:handler 展示确认内容(y/n/d 等),core 做输入收集 + /p 拦截(InterruptSignal 穿透) |

### 实施与真机迭代(四轮)

- **分支 confirm-interrupt**:InterruptSignal 无参触发 + dispatch 显式穿透 + 三防线(穿透 / 确认前置零副作用 / 幂等守卫)
- **真机第一轮**:write_file 用 line 模式时无确认直接改文件;工具运行中输入无回显;`/p` 提示没出现 → 修复:全模式确认 + 后台线程实时回显 + 提示文案
- **真机第二轮**:两次输入粘连(take_line 与监听线程并发竞态)→ threading.Lock 修复
- **设计调整**:`/p` 改纯触发(后缀忽略、无回显),打断后统一在打断处理点收集提示词,空提示词 = 取消打断
- **真机第三轮**:验证通过,但分支多轮 patch + 字节级修复,污染风险 → **干净重建**
- **干净重建**:从 main 全新 fork,6 个文件全新写入,逻辑 diff 确认一致,真机第四轮验证通过 → 合并 main

### 过程中的坑

1. **patch 工具 `\r` 转义陷阱**:new_string 里的 `\r` 被转成真实字节破坏源码,反复踩坑 4 次——最终用 chr(13)/chr(10) 规避,干净重建时彻底绕开
2. **cua-driver 故障**:无法驱动真实桌面,PTY 模拟 stdin 交互不可靠、bash 直连被墙需代理——最终由用户手动真机测试
3. **测试脚本自身 bug 多次**:mock 恒返回值误判、路径外确认抢输入序列、input prompt 不走 stdout——靠"断言与设计语义对齐"排查

## 二、STAR 法则总结

### S — Situation(情境)

用户提出"打断 + 提示"功能,核心诉求本身很简单(暂停循环 / 断点输入提示词 / 提示词进下一轮)。但**前期设计探讨聚焦在"功能怎么做",没有先锁定"架构归属"**——确认交互归谁、打断信号如何跨层传播、哪些层需要动。结果:每次需求细化(任何时间打断 → 隐藏输入 → 纯触发)都牵动 core + registry + 多个 handler,修改面反复扩散,经历了"实现 → 真机发现问题 → 修复 → 再发现问题"的多轮循环。

### T — Task(任务)

在最小改动、可演进的前提下落地该功能,并确保后续需求变化(随时打断、无回显、纯触发、空提示词取消)不被初始架构拖累;同时保证可验证(定向测试 + 真机)与可回退。

### A — Action(行动)

针对"牵一发而动全身",采取了一套组合策略:

1. **先定架构归属,再写代码** — 明确"交互与执行分离":确认**语义**归 handler(每种工具展示自己的确认内容),输入**收集与 /p 拦截**归 core(注入 `_confirm` 函数)。职责边界清晰后,后续改动只动归属方。

2. **信号通道先行** — 打断用 `InterruptSignal` 专用异常 + dispatch 显式穿透(不依赖字符串约定,不被异常兜底吞掉)。信号传播通道从第一天就固定,后面加路径(检查点 / 确认处)只是往通道上接。

3. **单点汇聚** — 所有打断路径(确认处 InterruptSignal、检查点监听)汇合到**一个处理点**(统一收集提示词)。后续"空提示词取消""统一问提示词"都只改这一处。

4. **接口向后兼容** — handler 的 `_confirm=None` 可选参数:直接调用 / 测试时跳过确认,新调用方式(dispatch 注入)与旧方式并存,降低迁移成本。

5. **零副作用约定** — 确认前置:handler 所有副作用严格排在确认之后,打断发生时没有需要回滚的状态。

6. **干净重建优于打补丁** — 多轮 patch + 字节级修复后代码风险累积(看不见的杂质),从 main 全新 fork 重写 6 个文件,逻辑 diff 验证一致,彻底消除污染顾虑。

7. **测试先行于真机** — 每轮改动先定向验证(mock 输入按 prompt 内容路由)+ pytest 回归,真机只验真机特有项(msvcrt 监听 / 回显),把试错成本压在自动化侧。

### R — Result(结果)

- 功能最终落地并合并 main,4 轮真机验证全部通过(确认 / 打断 / 提示词注入 / 取消)
- 后续小改动(write_file 确认改 while 重试、`/sessions del`、`/history del`)都只动单层,不再牵一发而动全身
- 验证体系沉淀:40+ 项定向验证 + pytest 72 项全绿
- 经验文档化(本文),"先定归属 → 信号通道 → 单点汇聚"成为后续功能开发的模板

## 三、可复用策略清单

对"前期构思不成熟导致后期大改"情景,按顺序执行:

```
1. 需求收敛期(动手前):
   □ 用 1-2 轮对话锁定"架构归属"——哪个层负责什么、信号怎么跨层传播
   □ 识别"会变的需求点",为它们预留扩展位(如可选的注入参数)

2. 实现期:
   □ 信号/数据通道先行并固定(异常、回调、注入),避免字符串约定
   □ 所有路径汇合单点处理(改一处 = 改全局)
   □ 副作用严格后置,可中断点之前零状态变更

3. 验证期:
   □ 定向测试覆盖行为语义(按 prompt 内容路由 mock 输入)
   □ 真机只验真机特有项;自动化能覆盖的不要上真机

4. 失控信号(多轮 patch 修补 / 字节级修复):
   □ 评估"干净重建"——从基线 fork 全新写入,逻辑 diff 验证一致
```

---

## 四、核心教训

1. **"牵一发而动全身"的根源不是需求变,而是职责没有在开始时分离清楚**——交互、执行、信号传播混在一起,任何需求变化都同时波及多层。
2. **前期多花一轮对话定架构归属,远小于后期每轮改动都动多层的成本**。本功能五轮设计收敛,前三轮都在补"归属"的课。
3. **当修补次数超过阈值(多轮 patch、字节级修复),干净重建是更便宜的选项**——保留旧分支作对照,逻辑 diff 验证一致性。
