1. 项目定位与设计原则

Dummy Agent 是一个从零构建的个人 AI 助理,目标不是复刻某个现成框架, 而是"真实使用、越用越好、低摩擦、可信、主动"。

三条不可让渡的原则

原则含义体现
单点收口 一件事只有一个入口,横切关注点收在一个门里 _parse_tool_arguments(解析)、_make_confirm(确认)、 _append_user_turn(用户消息)、project_messages(发送侧合法性)
可见性优先 不做复杂过滤;本地开发靠"看得见 + 人在终端前判断" 工具调用与结果全程打印;确认机制由用户按 y/n 决定
诚实优先于好看 验证不到的地方明确标注,不把推断当结论 文档里的"待验证""已知局限""文献空白"章节
本文件与 Phase 0 文档的关系
Phase 0 的设计文档保存在 design-phase0.html (英文 design-phase0-zh.html)。那份文档如实记录了 "当初决定不做什么",刻意不修改——决策的历史同样是有价值的信息。 本文件描述的是当前全貌。

选择理由

4. 架构

main.py            CLI 入口:命令分发、退出路径、会话锁释放
  └─ core.py       DummyAgent:工具循环 + 历史管理 + 注入 + 压缩触发
       ├─ llm.py               LLM 客户端(OpenAI 兼容封装 + 用量统计)
       ├─ prompt.py            system prompt
       ├─ compressor.py        上下文压缩(L1 折叠 / L2 增量摘要)
       ├─ session_store.py     持久化(会话/消息/归档/记忆/教训 + FTS + 锁)
       ├─ memory.py            跨会话记忆抽取
       ├─ skills_manager.py    技能索引 + 按需加载
       ├─ lessons.py           教训(错误学习)+ 工具失败判据
       ├─ self_improve.py      自我改进(检测→提案→批准→改→验证→回退)
       ├─ tool_guardrails.py   护栏:循环内实时止损(P1a)
       ├─ verify_stop.py       收尾前验证门(P1b)
       └─ tools/               工具注册表 + 5 个工具
            ├─ registry.py     注册 / dispatch / 确认注入 / 中断穿透
            └─ {...}.py        即插即用工具

一次 chat() 的完整流程

chat(user_input)                         ← 收口壳:try/finally 保证历史结算
 └─ _chat_impl(user_input)
     ├─ _ensure_session()                 ← 首次调用时建会话 + 取锁
     ├─ 注入:时间 / cwd / 记忆 / 技能索引 / 教训   ← 全部幂等
     ├─ 按轮清零:护栏计数、验证账本
     └─ for turn in range(max_tool_turns):        ← 默认 40,可配
          ├─ _maybe_compress()           ← 超过窗口 70% 时压缩
          ├─ project_messages(history)   ← 投影成合法 messages(发送侧单点)
          ├─ llm.chat(...)
          └─ 有 tool_calls?
               ├─ 是 → 逐个执行(护栏前/后挂钩、验证门记账)
               │       └─ 每批收尾 → 检查打断 → 落库
               └─ 否 → 验证门:改过代码但无证据? → 驳回(≤2 次)
                       否则落库 → 返回
     finally: _settle_history()          ← 无论怎么退出,补齐配对再落库

5. 对话历史:单一事实来源的演进

这是本项目最曲折的一条线,也是架构实验投入最多的地方。

5.1 问题

self.history 是一个共享可变列表,要同时满足四类不变量: 协议合法性(tool_calls↔tool 配对、角色交替)、持久性(save/load 无损)、 可压缩性、可读性(护栏/验证门要读"本轮"状态)。 这四类没有归属者,于是每个组件各自兜底,同一问题堆了 5~7 处修补点。

5.2 根因(实测得出)

非法状态是被主动写进磁盘的。
旧实现在 assistant(tool_calls) 与"同批全部 tool 回复"之间的 时间窗内就落库了。异常 / 强杀 / 断电只是"谁触发的",不是根因。

5.3 四路实测对照

判据分三组:AR-chat(经 chat 退出的历史必须合法)、 AR-stop(批次中途停机后磁盘必须合法)、 SOFT1(软标准:磁盘上从未出现过非法状态,通过加分)。

路线AR-stopSOFT1全套结论
路线 1 受管 History 类❌❌1 fail fail — end_tool_batch() 到不了"批次中途停机" (写入时看不到后续)
路线 2 投影器❌❌1 fail fail — 只管发送侧,碰不到落库时机
路线 3 单点收口✅❌0 fail 采纳 — 见下
路线 5 原子批次✅✅0 fail 技术最优,但牺牲 Ctrl+C 数据保留,未采纳

5.4 最终方案:单点收口(路线 3)

try:
    return self._chat_impl(user_input)   # 本体:工具循环
finally:
    self._settle_history()               # 唯一出口:补齐配对 + 落库

为什么不是更"干净"的路线 5——实测发现两者与 "Ctrl+C 保住已完成工具结果"互斥:

方案Ctrl+C 时已完成的工具结果磁盘上短暂存在半个批次
路线 3✅ 保住(实测留在磁盘)❌ 存在
路线 5❌ 整批全丢✅ 从不出现
判定依据:Ctrl+C 是高频操作(整个交互设计围绕它与 /p),且工具可能不可重复(构建/网络/硬件),丢结果是真实损失; 而"磁盘上短暂存在半个批次"不是问题——唯一的读取入口 resume_session() 会修复它(实测 7/7 种形态全部修好)。

6. 质量保障:三道闸门

闸门时机机制
P1a 工具护栏 循环内实时 两个信号:同一份失败反复出现(同工具+同参数+失败内容也相同)、 只读调用无进展(结果指纹重复)。第 2 次告警 / 第 6 次拦截
P1b 收尾验证门 模型想收尾时 本轮改过代码类文件却没拿出"全量测试通过"证据 → 驳回 (上限 2 次)。证据须晚于最后一次编辑
P2b 历史卫生 入口 / 咽喉 / 出口 配对双向修复(补缺失/删孤儿/去重/删尾部悬空块)+ 角色交替兜底

护栏为什么要求"失败内容也相同"

只按"工具+参数"计数会把"改一处、跑一次测试"(报错每次不同)误判成原地打转并拦死, 而验证门又要求"跑通全量测试"——两者互锁。实测结局是驳回 2 次后以 "无证据 + 声称完成"收尾,恰是验证门要防的事。

验证门的证据定义(档 A)

  • 必须是一次完整测试套件的 pytest 成功执行
  • 以 pytest 调用收尾——管道会掩盖退出码(pytest | tail 返回 tail 的 0)
  • 必须确实执行过(返回串带 [SHELL:,排除"用户取消")
  • 文档类扩展名豁免

7. 模块详解

7.1 core.py — 工具循环

  • _parse_tool_arguments:三层容错(json → json5 → 正则 + 反转义)
  • _append_user_turn:所有 user 消息的唯一入口,兼角色交替兜底; 系统合成的消息带 _meta.synthetic(压缩时不计入"保留最近 N 轮")
  • _repair_history:配对自愈,幂等、无改动时静默
  • _finalize_after_budget_exhausted:轮次用尽后剥掉工具再放一次调用, 让模型交代现状(而非硬停)

7.2 session_store.py — 持久化

  • load_history:忠实读取(不改写数据,自愈归 Agent 边界)
  • repair_tool_pairing:双向修复,返回统计 (backfilled/dropped_orphans/dropped_duplicates/dropped_dangling)
  • 会话锁:多进程防同会话双开导致历史交错
  • FTS5 双索引(中/英分词)+ tool_result_archive(折叠原文归档)

7.3 compressor.py — 上下文压缩

  • L1 折叠:超长 tool 结果截成 head+tail,原文进归档表(零 LLM 成本)
  • L2 增量摘要:旧摘要 + 新块 → 新摘要,切点在 user 边界
  • 压缩后跑 _validate_history,非法则回滚(压缩不能比不压缩更糟)
  • 断路器:连续失败 3 次 → 暂停该机制

7.4 verify_stop.py / tool_guardrails.py

两者都是纯控制器:只记账、只给判决,不执行动作、不打印——便于脱离 LLM 单测。

7.5 tools/registry.py — 工具注册表

  • 注册表模式:加工具只改 tools/__init__.py
  • dispatch 加固:异常兜底 + 结果规范化
  • 确认注入:拷贝参数后再注入 _confirm(不改写调用方 dict, 否则护栏前后签名不一致而失效)
  • InterruptSignal 穿透 dispatch,由 core 捕获处理 /p 打断

8. 关键决策汇总

决策理由
业务约束在 Agent 边界自愈,持久层忠实读取 塞进 load_history 会破坏"忠实读取"契约(实证:跑挂了既有测试)
确认语义归 handler,/p 拦截归 core 每种工具展示内容不同,但打断语义要全局一致
护栏默认硬停开启(有意偏离 Hermes 的默认关) 单用户交互式目标就是止损;环境变量可覆盖
护栏跳过"同工具不看参数"信号 重试有合法用途,只按工具名计数会误伤
验证门档 A:证据=一次全量成功率执行 全套通过隐含覆盖被改动文件,无需维护"模块→测试"映射表
轮次用尽后剥工具写总结,不硬停 几十轮的工具成果不该只换回一句"已停止"
加严加在"证据内容"轴,不是把阈值调小 dummy 的"判决者"轴已经是硬的(直接读退出码)
历史采用单点收口(而非原子批次) 见 §5.4:与 Ctrl+C 数据保留互斥,按频率 × 代价权衡
不做复杂 prompt injection 过滤 本地单用户,靠可见性 + 人在终端前判断

9. 已知局限

9.1 工具成败判据仍是字符串猜测

is_tool_error 已修掉双向误判(成功当失败 / 取消当成功),但仍是猜文案。 根治方案(结构化字段)已完成调研与设计,见 tool-result-structuring-design.md。

  • 已知残留:内容里恰好含 [错误] 字面量会误判(有测试记录此局限)

9.2 退出码语义未区分

grep 无匹配返回 1 是正常的,当前判据会当失败。 文献调研显示这是真实的学术空白(没有专门研究)。

9.3 其他

  • 无备份机制:session.db 单点,一条错误 DELETE 不可恢复
  • 归档表只进不出:折叠原文没有清理路径(实测当前仅 80 行,不紧急)
  • 软标准未达成:磁盘上会短暂存在半个批次(判定为可接受,见 §5.4)
  • 未做:流式输出、多平台网关
