1. 项目概述

Dummy Agent 是一个以学习为目的的项目，从零开始构建一个类 Hermes Agent 的 AI 智能体。Hermes 是 Nous Research 开发的开源 AI Agent 框架，具备工具调用、跨会话记忆、技能系统、多平台网关等丰富能力。

Dummy Agent 的目标不是复刻 Hermes 的全部功能——那是成千上万行代码和多年迭代的产物。相反，这个项目核心目标是：

  • 理解本质：通过亲手实现最小的 Tool-Calling Loop，彻底理解 Agent 的工作原理
  • 渐进构建：从极简原型开始，逐步添加每个组件，每一步都清楚"为什么要加"、"怎么加的"
  • 完整记录：每个决策都记录备选方案、选定方案、选择理由——形成可复用的知识

项目采用 DeepSeek API 作为 LLM 提供商，选择它的原因见技术选型章节。

2. Phase 0 目标与范围

目标

  1. 实现一个在工作站上可运行的最小 Tool-Calling Agent
  2. Agent 能调用 terminal 工具执行 shell 命令并查看结果
  3. 有交互式 CLI 界面，用户可实时观察 Tool Calling 过程
  4. 代码包含详细的中文注释，适合学习

明确不做（留到后续 Phase）

  • 会话持久化（SQLite 存储）
  • 上下文压缩（长对话处理）
  • 多工具支持（Phase 0 只有 terminal）
  • 流式输出
  • 安全审批机制
  • 多平台网关
  • 技能/记忆系统

成功标准

  • python main.py 能正常启动
  • 输入 API Key 后能连上 DeepSeek API
  • 输入 "当前目录有什么文件" → Agent 调 terminal("ls") → 返回结果
  • 输入 /help、/reset、/tools 等命令能正常响应

3. 技术选型分析

3.1 LLM 提供商：DeepSeek

方案优点缺点
✓ DeepSeek API（选定） - OpenAI 兼容 API，工具调用体验一致
- token 价格极低（输入 $0.27 / 百万 token）
- 128K token 上下文长度
- 无需海外信用卡 		- 有每日调用量限制（免费用户 3 RPM）
- 高峰期可能不稳定
OpenAI API - 最成熟的 tool calling 支持
- GPT-4o 工具调用准确率高		 - 需要海外支付方式
- 价格更高
- 国内访问不稳定
本地模型（vLLM / llama.cpp） - 完全离线
- 无 API 费用
- 数据不离开本机		 - 需要 GPU（显存需求高）
- 小模型的 tool calling 准确率低
- 搭建复杂度高
决策理由：Phase 0 需要快速验证 Tool-Calling Loop 是否工作。DeepSeek 的 OpenAI 兼容 API 意味着代码可以零改动切换到其他 provider，而极低的价格让实验成本几乎为零。本地模型对 Phase 0 来说搭建成本过高。

3.2 API 通信：OpenAI Python SDK vs 原生 HTTP

方案优点缺点
✓ OpenAI Python SDK（选定） - 自动处理认证、重试、超时
- IDE 类型提示完整
- Tool Calling 数据结构已封装好
- 20+ 个 provider 兼容同一 SDK 		- 多一层抽象（隐藏了 HTTP 细节）
- 额外依赖
原生 httpx/requests - 零依赖
- 完全透明，适合教学
- 完全控制请求/响应		 - 需要手动处理 JSON 序列化、认证头
- 需要手动解析 tool_calls
- 代码量翻倍
决策理由：Phase 0 要学的是 Agent 架构（循环、注册表、dispatch），而不是 HTTP 协议。SDK 把协议细节处理好，让代码聚焦在核心逻辑上。注释中会说明底层发生了什么。

3.3 框架选择：无框架 vs LangChain

方案优点缺点
✓ 零框架，纯 Python（选定） - 完全理解每一行代码在做什么
- 极低的学习曲线
- 完全灵活，不受框架约束
- 调试简单 		- 缺少高级功能（chain、memory 等）
- 需要自己实现基础设施
LangChain - 内置大量工具、memory、chain
- 社区大、文档多		 - 抽象层次太厚，底层不透明
- 调试困难
- 版本更新快，教程常过期
AutoGen / CrewAI - 多 Agent 开箱即用
- 高级编排能力		 - 对单 Agent 来说过度设计
- Phase 0 用不上
决策理由：这是学习项目。用框架就是"学习框架怎么用"，而不是"学习 Agent 怎么工作"。零框架意味着你需要理解 HTTP 调用、消息格式、tool_calls 的解析和回注——这些正是 Agent 的核心知识。

3.4 代码注释语言：中文

方案优点缺点
✓ 中文注释（选定） - 母语阅读，理解速度最快
- 对学习者最友好		 - 国际化时需替换
英文注释 - 业界惯例
- 不开新项目也能读		 - 理解速度慢（需脑内翻译）
决策理由：你是中文母语者，学习项目的第一目标是让你快速理解。注释的价值在于被阅读，而非符合"惯例"。

5. 模块详细设计

5.1 llm.py — LLM API 封装

设计：LLMClient 类
备选：模块级函数 vs 数据类 vs 封装类
选定方案：封装类（LLMClient），接收 api_key、base_url、model 三个参数初始化，提供 chat(messages, tools, ...) 方法。
为什么：类可以持有客户端状态（HTTP session、配置），避免调用方每次都传参数。使用 openai.OpenAI 库做底层封装，充分利用其对 OpenAI 兼容 API 的完善支持。

关键接口：

class LLMClient:
    def __init__(self, api_key: str, base_url: str, model: str)
    def chat(self, messages: list, tools: list | None,
             temperature=0.7, max_tokens=4096) -> ChatCompletionMessage

设计要点：

  • 温度 0.3：工具调用场景需要确定性输出。如果 temperature 太高，LLM 可能发明不存在的工具名或参数。Phase 0 固定为 0.3，后续可以做成可配置参数。
  • 空 tools 处理：如果 tools 参数是空列表或 None，就不传 tools 给 API。某些 provider 在 tools=[] 时会报错。
  • 错误处理：Phase 0 不做自动重试。API 错误通常意味着配置有问题（密钥无效、余额不足），需要人工介入。

5.2 tools.py — 工具注册表

设计：注册表模式
备选：if-else 中心调度 vs 注册表 vs 装饰器
选定方案：ToolRegistry 类 + 工厂函数 create_default_registry()。每个工具注册时同时提供 name、description、parameters schema、handler 函数。
为什么：注册表模式是 Agent 框架的标准实践。每加一个工具就是一个 registry.register(...) 调用，不修改现有代码（开闭原则）。注册表同时提供 get_tool_definitions() 给 core.py（生成发给 LLM 的 schema）和 dispatch() 给 tool calling loop（执行工具）。

核心数据结构：

Tool = {
    "name": "terminal",
    "schema": {
        "type": "function",
        "function": {
            "name": "terminal",
            "description": "...",
            "parameters": { "type": "object", "properties": {...} }
        }
    },
    "handler": terminal_handler  # Callable
}
⚠️ 安全警告：当前 terminal 工具使用 subprocess.run(shell=True)，直接将用户（或 LLM 生成的）命令传给系统 shell。这极其危险——prompt injection 攻击可以让 LLM 执行任意命令。Phase 1 必须添加命令审批机制和黑名单。

5.3 prompt.py — System Prompt 构造器

设计：运行时动态构造
备选：硬编码 vs 模板文件 vs 动态函数
选定方案：Python 函数 build_system_prompt(tool_names)，使用 f-string 将工具列表注入模板。
为什么：模板 + 动态注入是最平衡的方案。硬编码无法适应工具列表变化，YAML 模板文件对 Phase 0 过度设计。函数形式可以注入 OS 信息、时间戳等运行时的上下文。

提示词策略：

  • 身份定义："你是 Dummy Agent，一个正在学习工具调用的 AI 助手。"——诚实告知 Agent 的身份，它只是一个学习原型。
  • 工具描述：提示词中同时列出工具的文本描述（自然语言让 LLM 理解"什么时候用"）和 API 的 tools 参数（结构化 schema 让 LLM 知道"怎么调"）。
  • 行为规则：告诉 LLM 可以多步调用、遇到错误可以重试、不需要工具时直接聊天。
  • 环境信息：注入操作系统类型（Windows git-bash）和时间戳，帮助 LLM 理解其运行环境。

5.4 core.py — Agent 核心循环

设计：DummyAgent 类
备选：无状态函数 vs 生成器 vs 类
选定方案：DummyAgent 类，接收 llm_client 和 tool_registry 两个依赖。内部维护 self.history（消息列表）。提供 chat(user_input) -> str 和 reset() 方法。
为什么：对话历史需要跨多次 chat 调用保持。用类最自然，且依赖注入模式让测试和换组件都容易。后续需要持久化时，只需在类外部加一个 save/load 方法。

核心循环逻辑（伪代码）：

def chat(user_input):
    history.append({"role": "user", "content": user_input})

    for turn in range(MAX_TOOL_TURNS):       # 最多 10 轮
        response = llm.chat(history, tools)  # 调 LLM

        if response.tool_calls:              # LLM 想调工具
            history.append(response)         # 保存 assistant 消息（含 tool_calls）
            for tc in response.tool_calls:
                result = tools.dispatch(tc.function.name,
                                        json.load(tc.function.arguments))
                history.append({              # 回注结果
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": result
                })
            continue                          # 回到循环顶部，再调 LLM

        # LLM 回答了文本
        history.append({"role": "assistant", "content": response.content})
        return response.content

    return "[已达最大工具调用轮次]"

设计要点：

  • MAX_TOOL_TURNS = 10：安全网，防止 Agent 陷入无限工具循环。Hermes 默认是 90 轮。
  • 消息角色交替：OpenAI 格式要求严格交替 user → assistant → tool → assistant → user。违反会导致某些模型报错或行为异常。
  • tool_call_id 匹配：回注工具结果时，tool_call_id 必须和 assistant message 中的 id 完全一致。这是 LLM 关联"工具结果"和"工具调用"的唯一标识。
  • 诊断日志：Agent 在执行时打印 🛠 和 📝 标记，让使用者实时看到正在发生什么。

5.5 main.py — CLI 入口

设计：交互式 REPL
备选：交互式 vs 单次查询 vs Web UI
选定方案：while 循环 REPL，用户反复输入、Agent 反复响应。支持 /help、/reset、/tools、/history、/quit 等内置命令。
为什么：交互式模式可以观察 Agent 的每一个 tool calling 步骤，最适合学习。凭证优先读取环境变量（DUMMY_AGENT_API_KEY），其次是用户输入。环境变量方式更安全。

6. 关键决策汇总

决策方案理由（一句话）
开发策略迭代：最小原型 → 逐步加功能避免"大爆炸"式调试地狱，每步有可用的产出
LLM 提供商DeepSeek API（OpenAI 兼容）价格极低、无需海外信用卡、工具调用支持好
API 库OpenAI Python SDK协议细节已封装好，代码聚焦核心逻辑
整体框架零框架，纯 Python 标准库 + openai 包学习项目，需要理解每一行代码
工具管理注册表模式（ToolRegistry）开闭原则，加工具不改代码，查询和分发统一
提示词构造动态函数（f-string 注入工具列表）运行时自动适应工具变化，比模板文件更简单
状态管理类内维护 history 列表最自然的方式，依赖注入让组件可替换
错误处理传播不吞没（抛出异常）学习阶段需要完整 traceback 以便理解问题
凭证管理环境变量优先，终端输入后备安全最佳实践，方便持续使用
注释语言中文母语阅读速度最快，学习效果最好

8. 已知局限

  1. 无会话持久化：退出后历史丢失。重启需要重新输入 API Key。
  2. 无上下文压缩：长对话会超出 DeepSeek 的 128K token 限制（实际上因为来回 tool calling，消耗得很快）。
  3. 单工具：只有 terminal，没有文件读写、Web 搜索等能力。
  4. 不安全：terminal 工具直接 shell=True，无任何命令审批。
  5. 无流式输出：用户需等待整个响应完成才能看到结果。
  6. 无错误重试：API 调用失败直接抛出，不会自动重试。
  7. 不支持图片/文件输入：只能处理纯文本。
这些都是 Phase 1 的候选任务。增加会话持久化和上下文压缩是最优先的，没有它们 Agent 无法进行有意义的长时间交互。

9. 下一步规划

Phase 0 完成后，以下是下一阶段的候选方向（按优先级排序）：

Phase功能说明
1多工具（file I/O、web search）第 2、3 个工具，展示注册表的可扩展性
1会话持久化（SQLite）退出后能恢复对话，支持 /resume
1命令审批执行危险命令前要求用户确认
2上下文压缩超限时自动摘要早期历史
2流式输出逐字显示 LLM 回复，提升体验
2.env 配置文件不再需要每次输入 API Key
3跨会话记忆记住用户偏好和常用信息
3技能系统Agent 能保存和加载"技能"
3子 Agent 委托复杂任务派生子 Agent 并行处理
4消息平台网关接入 Telegram / Discord
4Cron 调度定时执行任务
路线图哲学：不一次性规划所有功能。每完成一个 Phase，根据使用体验来确定下一阶段做什么。有些功能你一开始以为需要，用起来发现不需要；有些你没想到的，用起来会发现缺了它不行。
