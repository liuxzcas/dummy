# 设计讨论:是否有必要做意图识别模块?(2026-08-10)

> 状态:讨论记录(scratch,未定稿)
> 背景:dummy-agent 是否需要一个"专门"的意图识别模块?如果需要,放哪个 phase?

## 结论

**现阶段不需要;不推荐单独立 phase 做意图分类器。**
若未来需要"意图"能力,融入两个已有阶段:Phase 2.4 的意图感知检索 + Phase 3 的技能路由。

## 分析

### 1. LLM 本身就是意图识别器

dummy-agent 架构里意图识别已存在且工作良好,分三层:

| 层 | 机制 | 在干什么 |
|----|------|---------|
| 语义理解 | LLM 读 user input + 上下文 | 理解"要什么" |
| 动作选择 | LLM 输出 tool_calls(工具名+参数) | 输出结构化意图 |
| 路由 | 工具 description 就是路由表 | 按意图选执行路径 |

工具调用本身就是意图的结构化输出。传统 agent 需要 NLU 是因为当时没有
通用语义理解;LLM 驱动架构已把这一步内化。

### 2. 独立分类器是负优化

- 多一次调用/多一套规则 → 延迟 + 新错误面
- 规则分类器误判会级联(把"看看这个文件"判成闲聊,链路就断);LLM 全上下文判断更稳

### 3. 出现以下信号才值得做显式模块(现在都不满足)

1. 成本敏感:简单请求占比高,想用轻量预筛跳过贵模型
2. 多模式分流:需要"查历史/执行任务/系统管理"等可预测的行为边界
3. 可解释性要求:审计/监管要"为什么调这个工具"
4. 自然语言命令:"看看昨天的会话"要映射到内部命令(现在靠 /xxx 显式前缀)

## 若未来要做:两个落点(不独立立项)

- **Phase 2.4 意图感知检索(推荐)**:跨 Session 记忆的注入 = 按当前请求意图
  检索最相关事实(PlugMem 思想)。意图只是检索的查询条件,不是独立模块。
- **Phase 3 技能路由**:技能选择即意图路由,技能 description 的质量决定路由质量。

## 一句话总结

意图识别已由 LLM + tool_calls 承担;真正需要"意图"的地方是 2.4 的检索
(查询条件)和 Phase 3 的技能路由(选择依据)——融入,而不是单独立项。
做玩具意图分类器当学习项目可以,塞进 dummy-agent 当产品模块是倒退。
