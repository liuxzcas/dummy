# Phase 4 Step 1 设计 — 任务规划与判据（Plan & Criteria）

> 版本号：**v0.2**（评审通过，待实施）
> 日期：2026-11-18
> 状态：设计定稿（§8.1 已决：采用方案 B）
> 定位：Phase 4「前馈学习」第 1 步。补的是现有学习机制的盲区——**只有摔了才学**。
> EN TL;DR: Design for a task-time planning + acceptance-criteria mechanism.
> The model writes a 3–5 step plan with a checkable "done" criterion per step
> *before* acting; the framework validates only the criterion's **syntactic shape**
> (`命令:` / `量:` / `计数:` prefix) — never its truth — and otherwise only records
> and reflects facts back. Modelled on `91-experiences/verification-gate-rollback-star.md`:
> protocol is code-guaranteed, semantics belong to the model.

---

## 0. 一句话

**开工前让模型自己写下「做什么、怎么算做完」，执行中框架只把这份计划与偏差摆回它眼前，不下判决。**

---

## 1. 为什么现在要做（数据依据）

### 1.1 现有学习机制是"负反馈查表"，且对沉默的低效失明

| 通道 | 文件 | 触发信号 | 学到的形态 |
|---|---|---|---|
| lessons | `lessons.py:24` `CORRECTION_PATTERNS` | 用户说"错了/不对/重来"或工具报错 | "做 X 会错，应该 Y"（查表） |
| memories | `memory.py` | 用户陈述事实/偏好 | 事实条目 |
| skills | `skills_manager.py` | 用户说"固化一下" | 流程文档 |
| self_improve | `self_improve.py:36` `MIN_ERRORS=3, ERROR_RATE_THRESHOLD=0.30` | 工具错误率超阈值 | 改代码提案 |

四条通道的输入**全部是"已经出错"**。日志实测（`logs/` 54 个会话）：

1. `conversation_20261117_181427.json`：一条改图脚本重复执行 **51 次**（#189→#681），全程零工具报错、零用户纠正。
2. 同会话 #273→#289：字号够→被裁出画布→重排→又遮挡→重排，**6 轮全部"成功"**。
3. lessons 库现有 39 条，hits 最高的 5 条（47/53/45/46/43）全是环境类硬约束（权限、路径、超时、编码、通配符）——**查表项会迅速饱和**。

结论：最贵的一类失败**不产生任何错误信号**，现有四条通道都学不到。

### 1.2 模型不是不会规划，是规划没有生存压力

44 个真实任务会话的统计：

| 首轮 assistant 文字量 | 会话数 | 平均工具调用 | 平均重复调用 |
|---|---|---|---|
| >300 字（写了计划） | 3 | 51.3 | 2.7 |
| 0–60 字（直接开干） | 33 | 58.2 | 11.6 |
| 60–300 字（半计划） | 8 | 169.1 | 51.8 |

- **33/44 完全跳过规划**，而它们并没有失败——因为错误是延迟出现的，没人因此付出即时代价。
- `prompt.py:91`「一次只调用一个工具」在结构上鼓励**边走边看**，天然抑制先想清楚。
- 中间档最惨（169 次调用 / 51.8 次重复）：**任务越重越需要规划，也越容易跳过规划**。

### 1.3 有规划意识，但写完就扔

`conversation_20261117_181427.json` #423：「我先全局扫一遍」→ 从关键词扩到全文 → #427「同类问题可能不止关键词，我把全文导出来逐页看语气」。
这是模型**在临时自己造判据**，判据用完即弃，没有沉淀、不跨任务复用。

## 2. 明确不做的事（吸取 2026-09 的教训）

`91-experiences/verification-gate-rollback-star.md` 记录了两个机制被**推翻**的过程：

| 老机制 | 做法 | 实测代价 |
|---|---|---|
| 收尾验证门 `verify_stop.py` | 硬规则判决"你有没有证据" | 一个 4 次调用能做完的任务跑了 **66 次**，80% 消耗在门的连锁反应 |
| 工具护栏 | 达到阈值就**拦截**调用 | 与验证门互锁：门要求跑、护栏禁止跑 |

推翻后确立的原则（同文档 §4.3 用户原话）：

> 让 LLM 来选取自己需要的东西，分析并得出结论，agent 要做的是提供运行过程中产生的相关信息，而不是代替 LLM 去做判断。

**本设计必须遵守的三条红线**：

1. ❌ **不做判决**：不判"计划够不够好"、不判"这步算不算完成"、不驳回、不计次、不设上限。
2. ❌ **不做拦截**：不因为"你没写计划"就阻止模型调工具。
3. ✅ **只做可见性**：把模型自己写的计划、实际执行轨迹、两者的偏差，摆回它眼前。

现有 `turn_context.py` 已经建立了这个正确范式（只陈述事实），本设计**复用它的位置和哲学**，不新造第二个判决器。

## 3. 机制设计

### 3.1 三个部件

```
┌──────────────────────────────────────────────────────────┐
│ 1. 计划板 (Plan)   —— 模型写，框架存，随时可改            │
│ 2. 判据 (Criteria) —— 每步一条"怎么算过"，写在计划里       │
│ 3. 偏差回显 (Drift) —— 中途/收尾时把事实摆回模型眼前      │
└──────────────────────────────────────────────────────────┘
```

### 3.2 计划板的形态

不新造工具。**用现有 `write_file` 写入 `garage/_plan.md`**，格式约定 4 行：

```markdown
## 目标
一句话说清这次要交付什么。

## 步骤
1. [判据: 具体怎么验] 动作描述
2. [判据: ...] 动作描述
3. [判据: ...] 动作描述

## 何时停下来问
什么情况下不自己硬扛，直接问用户。
```

理由：
- `garage/` 已在 `.gitignore` 里（`.gitignore` 末尾 `garage/*`），不污染仓库。
- 不需要新工具、不需要新表、不需要改协议——**零 API 变更**。
- 模型本来就会写文件，学习成本为零。

### 3.3 什么时候要求写（门槛）

**不是所有任务都写**，否则违反"低摩擦"原则。触发条件（满足任一）：

| 条件 | 依据 |
|---|---|
| 预计工具调用 ≥ 3 次 | 日志平均 12.7 次/轮，3 次以下是闲聊级 |
| 任务要产出交付物（文件/PPT/报告/代码改动） | 交付物才有"做得对不对"的问题 |
| 用户一句话里含 ≥2 个动词性要求 | 多要求必然要多步骤 |

短任务（问个问题、跑个命令、读个文件）**明确不要求**——这是设计的一部分，不是疏忽。

### 3.4 判据怎么写才算合格（唯一的质量约束）

一条合格判据必须**能被第三方机械复现**。为了让它可被校验而不必做语义判决，
**判据必须以前缀声明形态**，三种前缀：

| 前缀 | 形态 | 例子 | 反例（不合格） |
|---|---|---|---|
| `命令:` | 可执行命令及其通过条件 | `命令: pytest tests/test_x.py -q 退出码 0` | "测试都过了" |
| `量:` | 可计算的量 + 阈值 | `量: 图内最小字号 × 显示/画布比 >= 12pt` | "字看起来够大" |
| `计数:` | 可枚举的计数归零 | `计数: content_20.py 里 "学生" 出现次数 == 0` | "语气改好了" |

**框架只校验前缀**（方案 B，2026-11-18 评审通过）：

- ✅ 校验：这一行的判据是否以 `命令:` / `量:` / `计数:` 三者之一开头。
- ❌ 不校验：命令能不能跑、阈值合不合理、计数对象对不对——**这些一律归模型**。

依据：`turn_context.py` 文件头已划清边界——「协议合法性 → 代码硬保证；语义判断 → 模型」。
判据行的**前缀是协议**，判据的**内容是语义**。这条界线让本机制有了约束力，又没有替模型判对错，
从而避开 `verify_stop` 的覆辙。

> **已知可被绕过**：模型写 `计数: 无` 或 `量: 随便 >= 0` 能通过前缀校验。
> 这是**有意接受**的代价——校验的是"你有没有声明一种可复现的形态"，不是"你的声明是否真诚"。
> 真诚问题留给 §3.5 的回显：判据声称的东西与实际执行对不上时，事实会摆在模型面前。

这条约束是**本设计与"走过场的计划"的分界线**。日志已证明：模型知道"要看图"，
但不知道"看到什么算过"，于是重排 6 轮（§1.1 第 2 条）。

### 3.5 执行中的回显（Drift）

复用 `turn_context.py` 的既有位置（`core.py:994-1005` 收尾处 + 可在中途插入）。

**回显内容只有事实，没有评价**：

```
[计划对照]
你开工时写的计划(garage/_plan.md):
  1. 改字号      [判据: 最小字 ≥14pt, 且 显示/画布比 ≥0.85]
  2. 重排布局    [判据: 逐页读图确认无遮挡]
  3. 导出并复检  [判据: 31 页全部导出成功]

本轮实际:
  - 步骤 1 已执行 7 次(改动 gfx.py 6 次)
  - 步骤 2 未开始
  - 步骤 3 未执行
  - 判据 1 最近一次核对: 无记录
```

关键设计：
- **不写"你偏离了计划"**——只写"步骤 2 未开始"。
- **不写"你该补判据了"**——只写"判据 1 最近一次核对: 无记录"。
- 模型看到"6 次改动 / 0 次核对"，自己会得出"我在盲调"的结论。

### 3.6 触发回显的时机（这是唯一需要新代码的地方）

| 时机 | 触发条件 | 目的 |
|---|---|---|
| 中途 | 同一文件被改 ≥3 次，且期间无任何 terminal 执行 | 打断盲调循环 |
| 收尾 | 模型要收尾时（复用现有 `build_stop_context` 位置） | 让模型自查 |

第一条来自实测：51 次改图循环的特征就是"改文件 / 没跑任何检查"交替。这是**观察**，不是判决——框架只报告这个事实。

### 4.1 `read_plan()` 的判定边界（实现时必须遵守）

```python
CRITERION_PREFIXES = ("命令:", "量:", "计数:")

def criterion_kind(step_line: str) -> str:
    """返回 cmd / num / count / none。只看前缀，不看内容。"""
    for kind, prefix in zip(("cmd", "num", "count"), CRITERION_PREFIXES):
        if prefix in step_line:
            return kind
    return "none"     # 未声明判据 —— 只作为事实报告，不拦截
```

- `none` **不是错误**，只是一个被如实记录的状态，会出现在 §3.5 回显的「判据: 未声明」里。
- 函数**不得**解析数字、不得执行命令、不得比对阈值。

## 5. 验证方法

### 5.1 单元测试
- 门槛：会话题必须要求计划，短任务不得要求。
- **前缀校验**：`命令:`/`量:`/`计数:` 三种合法前缀各一条通过；无前缀的步骤返回 `none`（记为"未声明"，**不抛出、不拦截**）。
- 解析容错：4 种畸形 `_plan.md`（无判据、无步骤、空文件、非 markdown）都不得抛异常。
- drift：同文件改 3 次且无 terminal 时，回显里出现"步骤 N 已执行 X 次"。
- **判决禁令（核心防护）**：对 `build_stop_context()` 输出做断言，不得含 `偏离`、`应该`、`必须`、`你没有` 等判决性措辞。这条对应 `verify_stop` 被推翻的根本原因，是防止机制退化的护栏。

### 5.2 回归对照（关键）
用同一个真实任务跑两遍：
1. 关闭机制（`DUMMY_PLAN=0`）：基线。
2. 开启机制：对照。

比三个数：工具调用总数、重复调用数、用户纠正次数。
**判定标准不是"更少就是更好"**——如果规划本身花了 5 次调用而任务总共才 8 次，那就是负收益。参考 `verify_stop` 的教训：66 次 vs 4 次的差别说明，机制本身的开销必须被计入。

### 5.3 可回退
- 环境变量 `DUMMY_PLAN=0` 一键关闭，行为回到现状。
- `garage/_plan.md` 在 gitignore 内，不产生仓库污染。

## 6. 已知风险与对策

| 风险 | 依据 | 对策 |
|---|---|---|
| **计划变成走形式** | 日志中"中间档"8 个会话平均 169 次调用 | §3.4 判据三形态约束；但**不强制执行**，只在回显里暴露"无判据" |
| **规划开销吃掉收益** | `verify_stop` 门 66 次 vs 情况说明 4 次 | §3.3 门槛；§5.2 回归对照必须算机制自身开销 |
| **只验写下来的维度** | `conversation_20261117_181427` #396：用户把 1:1 降级成阈值，模型立刻改写规范、丢掉机制理解 | 计划板允许随时改；回显同时展示"计划改过几次"，让偏离可见 |
| **又一个堆放处** | garage 已是 385 MB | `_plan.md` 单文件、每轮覆盖，不做历史归档 |
| **与 lessons 重复** | lessons 也产"规则" | 分工：**lessons 存跨任务规则，_plan.md 存本次任务契约**；收尾时 lessons 可取 plan 作输入 |

## 7. 与 Phase 4 其余部分的关系

本步只做「计划 + 判据 + 回显」。**有意不做**的两件事（留给后续步骤，避免一次做太大）：

1. **check 库**（可复用验证器）——等本步跑出真实条目再建，否则是个空库。
2. **机制笔记**（因果链沉淀）——它比判据更值钱（判据是查表、机制能外推），但需要先有本步产出的"判据长什么样"作为素材。

## 8. 待定项（评审时定）

### 8.1 【已决 2026-11-18】判据质量由谁把关——采用方案 B

原草案的自相矛盾：正文坚持「框架一个字都不评」，但那样判据三形态约束就只是劝告；
若框架检查「判据是否可复现」，又回到 `verify_stop` 被推翻的老路。

**决定：方案 B —— 框架只校验判据行的语法前缀，不校验内容真伪。**

| 方案 | 结论 |
|---|---|
| A. 纯劝告 | 弃用（约束力为零） |
| **B. 只校验形状** | **采用**（协议归代码，语义归模型） |
| C. 事后回填 | 弃用（反馈滞后） |

落地要求（已并入 §3.4、§4、§5.1）：
1. 判据必须以 `命令:` / `量:` / `计数:` 之一开头；否则该步骤视为「未声明判据」，在回显中列出。
2. 框架**不做**任何内容校验，也不因为缺前缀而拦截任何工具调用。
3. 单元测试必须同时覆盖：①三种合法前缀通过；②缺前缀被识别为「未声明」；
   ③**输出中不得出现判决性措辞**（`偏离`/`应该`/`必须`/`你没有`）——第三点是防止机制退化的护栏。

已知并接受：模型可写 `计数: 无` 绕过前缀校验。真诚性由 §3.5 回显承担，不由代码承担。

### 8.2 其余待定

2. 回显时机 ①（同文件改 ≥3 次且无检查）阈值取 3 还是 5？
