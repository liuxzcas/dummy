1. Project Overview

Dummy Agent is a learning-oriented project that builds an AI agent similar to Hermes Agent (Nous Research's open-source agent framework) from absolute scratch.

The goal is not to replicate all of Hermes' features — that's thousands of lines of code and years of iteration. Instead, the core objectives are:

  • Understand the essence: Implement the minimal Tool-Calling Loop by hand to truly understand how agents work
  • Build incrementally: Start with a minimal prototype, add components one by one, knowing exactly why each is needed
  • Document everything: Every decision records alternatives, chosen solution, and rationale — building reusable knowledge

The project uses DeepSeek API as its LLM provider — rationale is in the Technology Choices section.

2. Phase 0 Goals & Scope

Goals

  1. A working minimal Tool-Calling Agent that runs on the development machine
  2. Agent can call a terminal tool to execute shell commands and see results
  3. Interactive CLI so the user can observe each tool-calling step in real time
  4. Code has detailed comments in Chinese for learning purposes

Explicitly Out of Scope

  • Session persistence (SQLite storage)
  • Context compression (long conversation handling)
  • Multiple tools (Phase 0 only has terminal)
  • Streaming output
  • Safety/approval mechanism
  • Multi-platform gateway
  • Skills/memory system

Success Criteria

  • python main.py starts without errors
  • Connects to DeepSeek API with user-provided API key
  • "List files in current directory" → Agent calls terminal("ls") → returns results
  • Built-in commands: /help, /reset, /tools, /quit all work

5. Module Design

5.1 llm.py — LLM API Wrapper

Design: LLMClient class
Alternatives: module-level functions vs dataclass vs wrapper class
Chosen: LLMClient(api_key, base_url, model) class with a chat(messages, tools) method, wrapping the openai.OpenAI SDK.
Why: A class holds client state (HTTP session, config), avoiding repetitive parameter passing. The OpenAI SDK handles auth, serialization, and protocol compliance. DeepSeek's API is fully compatible.

Key design points:

  • Temperature 0.3: Tool calling needs deterministic output. High temperature causes hallucinations (invented tool names, malformed arguments).
  • Empty tools handling: Skip the tools parameter when no tools are provided — some providers reject empty tool arrays.
  • No retry: Phase 0 propagates errors. API failures usually mean wrong credentials or insufficient balance — human intervention needed.

5.2 tools.py — Tool Registry

Design: Registry pattern
Alternatives: if-else central dispatch vs registry vs decorators
Chosen: ToolRegistry class + factory create_default_registry(). Each tool registers its name, description, JSON Schema, and handler.
Why: The registry pattern is the standard in agent frameworks. Adding a tool is one registry.register(...) call — no existing code changes (open/closed principle). The registry provides both tool definitions (for the API call) and dispatch (for the loop).
⚠️ Security: The terminal tool uses subprocess.run(shell=True). This is extremely dangerous — a prompt injection attack could execute arbitrary commands. Phase 1 must add command approval and blacklists.

5.3 prompt.py — System Prompt Builder

Design: Runtime dynamic construction
Alternatives: hardcoded string vs template file vs dynamic function
Chosen: Python function build_system_prompt(tool_names) using f-string injection.
Why: Dynamic injection is the sweet spot — hardcoding can't adapt to tool changes, YAML templates are over-designed for Phase 0. The function can also inject runtime OS info and timestamps.

Prompt strategy:

  • Identity: "You are Dummy Agent, an AI assistant learning tool calling." — honest about being a learning prototype.
  • Tool description in two places: Natural language in the prompt (so LLM knows when to use tools) and structured schema in the API tools parameter (so LLM knows how).
  • Environment info: OS info and timestamp help the LLM understand its runtime context.

5.4 core.py — Agent Loop

Design: DummyAgent class
Alternatives: stateless functions vs generator vs class
Chosen: DummyAgent(llm_client, tool_registry) class. Maintains self.history. Provides chat(user_input) → str and reset().
Why: Conversation history must persist across multiple chat turns. A class is the most natural approach, and dependency injection makes testing and component swapping easy.

Core loop (pseudocode):

def chat(user_input):
    history.append({"role": "user", "content": user_input})

    for turn in range(MAX_TOOL_TURNS):       # max 10
        response = llm.chat(history, tools)

        if response.tool_calls:              # LLM wants tools
            history.append(response)
            for tc in response.tool_calls:
                result = tools.dispatch(tc.function.name,
                                        json.load(tc.function.arguments))
                history.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": result
                })
            continue

        # LLM responded with text
        history.append({"role": "assistant", "content": response.content})
        return response.content

    return "[Max tool turns reached]"

Key points:

  • MAX_TOOL_TURNS = 10: Safety net against infinite tool loops. (Hermes defaults to 90.)
  • Role alternation: OpenAI format requires strict user → assistant → tool → assistant → user alternation.
  • tool_call_id matching: The tool_call_id when injecting results must match the original call ID exactly — this is how LLMs correlate results with calls.
  • Diagnostic logging: 🛠 and 📝 markers let the user observe each step in real time.

5.5 main.py — CLI Entry

Design: Interactive REPL
Alternatives: interactive vs one-shot query vs Web UI
Chosen: while-loop REPL with built-in commands (/help, /reset, /tools, /history, /quit). Credentials read from environment variables first, fallback to input.
Why: Interactive mode lets you observe every tool-calling step — best for learning. Environment variables are more secure than typing keys every time.

7. Execution Walkthrough

Example: user asks "List files in current directory":

User: "List files in current directory" Step 1: Build messages history = [ {"role": "system", "content": "You are Dummy Agent..."}, {"role": "user", "content": "List files in current directory"} ] Step 2: Call LLM with tools definition llm.chat(messages=history, tools=[terminal_schema]) Step 3: LLM returns tool_call { "content": null, "tool_calls": [{ "id": "call_abc123", "function": { "name": "terminal", "arguments": '{"command": "ls"}' } }] } Step 4: Execute tool tools.dispatch("terminal", {"command": "ls"}) → subprocess.run("ls", shell=True) → returns "main.py\ncore.py\nllm.py\n..." Step 5: Inject result history.append({ "role": "tool", "tool_call_id": "call_abc123", "content": "main.py\ncore.py\nllm.py\n..." }) Step 6: Call LLM again (sees ls output) llm.chat(messages=history, tools=[...]) → returns "The directory contains: main.py, core.py, llm.py, ..." Step 7: Return to user print("The directory contains: main.py, core.py, llm.py, ...")

8. Known Limitations

  1. No session persistence: History lost on exit. Must re-enter API key on restart.
  2. No context compression: Long conversations hit DeepSeek's 128K token limit fast (tool calling consumes tokens rapidly).
  3. Single tool: Only terminal. No file I/O, web search, etc.
  4. Unsafe: shell=True with no command approval.
  5. No streaming: Users wait for the complete response.
  6. No retry: API errors propagate immediately.
  7. Text-only: No image/file input support.
These are Phase 1 candidates. Session persistence and context compression are the highest priority — without them, meaningful long interactions are impossible.
