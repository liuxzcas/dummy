1. Scope & Design Principles

Dummy Agent is a personal AI assistant built from scratch. The goal is not to replicate an existing framework, but to serve as an assistant that is genuinely used, improves with use, stays low-friction, can be trusted, and acts proactively.

Three non-negotiable principles

PrincipleMeaningWhere it shows up
Single choke point One entry per concern; cross-cutting concerns live behind one door _parse_tool_arguments (parsing), _make_confirm (confirmation), _append_user_turn (user messages), project_messages (outbound validity)
Visibility over filtering No elaborate sanitizing; local development relies on visibility plus a human at the terminal Every tool call and result is printed; the user decides via y/n
Honesty over polish What could not be verified is labelled as such; inference is never presented as evidence The "unverified", "known limitations", and "literature gap" sections throughout the docs
Relationship to the Phase 0 document
The Phase 0 design document is preserved at design-phase0.html (Chinese: design-phase0-zh.html). That document records what we deliberately chose not to build, and is intentionally left unedited — the history of a decision is itself valuable information. This document describes the current state.

2. Who Decides: Code or Model?

This is the project's most central architectural principle, and it only became clear after two rounds of correction (the history layer and the verification gate). It answers: given a problem, should it become a rule, or go to the model?

2.1 Test: is it protocol/fact, or semantics?

ClassCharacteristicOwnerWhy
Protocol / fact One correct answer, independent of intent Code, as a hard guarantee The model cannot violate a protocol however smart it is; this needs execution, not understanding
Semantics / values Depends on intent, context, domain knowledge; may have no unique answer The model (the agent only supplies information) Rules cannot enumerate reality; any attempt produces absurdity on the cases that were not enumerated

2.2 The concrete split

QuestionClassOwnerStatus
Is the tool_calls ↔ tool pairing complete Protocol Code Done — history layer (repair_tool_pairing / _settle_history)
Do roles alternate (system/user/assistant/tool) Protocol Code Done — _append_user_turn / close_interrupted_tool_sequence
Should this rm run Values (human) Human Done — confirmation (y/n)
Is this call "spinning in place" Fact (behavioural) Code Done — tool guardrails (same args + identical failure output)
Is the task done Semantics Model Done — turn summary (states facts, no verdict)
What counts as verified Semantics Model Done — as above
Is the artifact correct Semantics Model + human Done — via visibility (everything printed) plus a human at the terminal
Counter-example: what happens when code overreaches into semantics (measured)
The former verify-on-stop gate encoded "is the task done / what counts as evidence" as 346 lines of hard rules. Three measured bugs were three symptoms of one disease — rules cannot enumerate reality:
  • .bat missing from the exemption list → "prove the launcher works by running the full pytest suite" (logically absurd)
  • "Evidence may only be a full pytest pass" → the model's actually-relevant checks (drill tests, line-ending inspection) were never accepted
  • "Cap of 2" reset per turn → one user remark and the safety valve reset
Outcome: 66 tool calls, 8 irrelevant pytest runs, turn budget exhausted, task interrupted.

2.3 What this principle means for "verification"

There is no universal verification criterion. "What counts as verification" depends on what is being verified:

What you are doingWhat counts as verificationWho can judge
Changing dummy's own Python code Running dummy's pytest Code can decide (green implies the change is covered)
Writing a launcher .bat Running it and seeing whether it starts Only the model/human can judge what "it started" means
Writing a ROS2 node Running it in the target environment, checking topics/services As above
Building a quiz web page Clicking through it in a browser, checking grading is correct As above
Key realisation: dummy's pytest is unrelated to the target code being written
Every test under tests/ imports dummy's own modules (core / compressor / session_store / tool_guardrails …) — they test dummy itself.
But this project's actual usage is using dummy to write other code (launchers, ROS2 scripts, web pages). The two coverage sets are disjoint: have dummy write a ROS2 node, and a green run of dummy's own pytest proves nothing about whether that node runs.
So "pytest is green" holds only for the first kind of task (changing dummy itself), and the latter three — which are the daily reality — are not covered. Fixing on one criterion and applying it to every task is a design error.

2.4 What code should still do (even when judgement goes to the model)

"Don't decide for the model" does not mean "do nothing". The code's job is to give the model everything it needs to decide:

  • Record faithfully what changed, what ran, and what the results looked like (including raw error text — never pre-digested into "success/failure")
  • Preserve raw signals — exit codes, error output, file paths — without filtering on the model's behalf
  • Impose no artificial thresholds: no rejection, no counting, no cap, no exemption list
  • Stay hard where hardness is required: protocol validity (or a 400), safety confirmation (a human judgement)

In one line: the agent makes the facts visible; the model draws the conclusion. This is §1's "visibility over filtering" applied at another level.

       ├─ llm.py               LLM client (OpenAI-compatible wrapper + usage accounting)

       ├─ compressor.py        context compression (L1 folding / L2 incremental summary)
       ├─ session_store.py     persistence (sessions/messages/archive/memories/lessons + FTS + locks)
       ├─ memory.py            cross-session memory extraction
       ├─ skills_manager.py    skill index + on-demand loading
       ├─ lessons.py           lessons (error learning) + tool-failure predicate
       ├─ self_improve.py      self-improvement (detect → propose → approve → edit → verify → roll back)
       ├─ tool_guardrails.py   guardrails: real-time loss-cutting inside the loop (P1a)
       ├─ turn_context.py      turn summary (states facts, issues no verdict)
       └─ tools/               registry + 5 tools
            ├─ registry.py     register / dispatch / confirm injection / interrupt passthrough
            └─ {...}.py        plug-and-play tools

Anatomy of a single chat()

chat(user_input)                         ← shell: try/finally guarantees history settlement
 └─ _chat_impl(user_input)
     ├─ _ensure_session()                 ← create session + acquire lock on first call
     ├─ inject: datetime / cwd / memories / skill index / lessons   ← all idempotent
     ├─ per-turn reset: guardrail counters, verification ledger
     └─ for turn in range(max_tool_turns):        ← default 40, configurable
          ├─ _maybe_compress()           ← compress past 70% of the context window
          ├─ project_messages(history)   ← project into valid messages (outbound choke point)
          ├─ llm.chat(...)
          └─ tool_calls present?
               ├─ yes → execute each (guardrail pre/post hooks, ledger bookkeeping)
               │        └─ batch end → check interrupts → persist
               └─ no  → append a one-off "turn summary" (what changed / what ran)
                        → persist → return
     finally: _settle_history()          ← whatever the exit path, repair pairing and persist

6. Conversation History: Evolving a Single Source of Truth

This is the most winding thread in the project, and where most architecture effort went.

6.1 The problem

self.history is a shared mutable list that must satisfy four classes of invariant simultaneously: protocol validity (tool_calls↔tool pairing, role alternation), durability (lossless save/load), compressibility, and readability (guardrails and the verification gate read per-turn state). These four had no owner, so every component added its own fallback — five to seven patches for a single problem.

6.2 Root cause (established empirically)

Illegal state was actively written to disk.
The old implementation persisted inside the time window between assistant(tool_calls) and the remaining tool replies of the same batch. Exceptions, hard kills, and power loss were merely who triggered it, not the root cause.

6.3 Four-way measured comparison

The criteria fall into three groups: AR-chat (history must be valid on any exit through chat), AR-stop (disk must be valid after a mid-batch stop), and SOFT1 (soft criterion: illegal state never appears on disk — bonus, not a gate).

RouteAR-stopSOFT1SuiteVerdict
1 — Managed History classfailfail1 failure fail — end_tool_batch() is unreachable when the batch stops mid-flight (write time cannot see the future)
2 — Projectionfailfail1 failure fail — only covers the send side, never touches persist timing
3 — Single choke pointpassfail0 failures adopted — see below
5 — Atomic batchpasspass0 failures Technically best, but sacrifices Ctrl+C data retention — not adopted

6.4 Final design: single choke point (route 3)

try:
    return self._chat_impl(user_input)   # body: the tool loop
finally:
    self._settle_history()               # single exit: repair pairing + persist

Why not the "cleaner" route 5 — measurement showed the two are mutually exclusive with preserving completed tool results on Ctrl+C:

ApproachCompleted tool results on Ctrl+CHalf-batch briefly on disk
Route 3Preserved (measured on disk)Yes
Route 5Entire batch lostNever
Decision basis: Ctrl+C is a high-frequency operation (the whole interaction design is built around it and /p), and tools may be non-repeatable (builds, network, hardware) — losing results is a real cost. A half-batch briefly on disk is not a problem: the only read path, resume_session(), repairs it (7 of 7 shapes verified).

7. Quality Gates: Two Hard Gates Plus a Layer of Information

A direction correction happened here (2026-09-16)
The former "P1b verify-on-stop gate" was a judge: 346 lines of hard rules (full pytest / later-than-edit / exemption list / max 2 attempts) issuing verdicts on "is the task done" and "what counts as evidence", then rejecting.
A real conversation transcript (creating a Windows launcher) exposed three bugs — three symptoms of one disease: rules cannot enumerate reality:
  • Attempt cap reset per turn: one user remark → counter zeroed → the same problem rejected again (4 rejections measured). The safety valve was ineffective
  • .bat missing from the exemption list → the model was required to "prove the launcher works by running the full pytest suite" (logically absurd). It ran pytest ~8 times chasing an unmeetable rule
  • Only one evidence shape recognised → the model's actually-relevant checks (drill tests, line-ending inspection) were never accepted; the only accepted path proved nothing. The turn budget ran out and the task was interrupted
Correction: give the judgement back to the LLM; the agent only supplies the information produced while running. Consistent with the existing "visibility over filtering" principle.
MechanismTimingWhat it doesNature
Tool guardrails Real time, in the loop Two signals: the same failure repeating (same tool + args + identical failure output), and read-only calls making no progress (repeated result fingerprint). Warn on the 2nd, block on the 6th Loss-cutting (a loop is a behavioural fact; no semantic understanding needed)
Turn context
(formerly the verify gate)		 When the model tries to finish States what changed, what ran, what the results looked like as a narrative appended to context (once only). No verdict, no rejection, no counting, no cap, no exemption list Supplies information (judgement stays with the model)
History hygiene Entry / throat / exit Bidirectional pairing repair (backfill missing / drop orphans / dedupe / drop trailing dangling block) plus role-alternation fallback Hard guarantee (API protocol — the LLM cannot violate it)

What code still guarantees (these are not semantic judgements)

  • History protocol validity (tool_calls↔tool pairing, role alternation) — an API protocol the LLM cannot violate; invalid history yields an immediate 400
  • Safety confirmation (should this rm run) — a human judgement, not delegated to the LLM

Everything else — "is the task done", "is it correct", "what counts as evidence" — is a semantic judgement the model now makes itself from the information the agent supplies, rather than one made for it by hard-coded rules.

Why the guardrail requires "identical failure output"

Counting by tool + args alone flags the normal edit-run-edit cycle (same command, different error each time) as spinning and blocks it. That predicate was fixed during the hard-rules era and is retained.

8. Module Reference

8.1 core.py — the tool loop

  • _parse_tool_arguments: three-tier tolerance (json → json5 → regex + unescape)
  • _append_user_turn: the single entry for user messages, doubling as the role-alternation fallback; synthetic messages carry _meta.synthetic so compression does not count them toward "keep last N turns"
  • _repair_history: pairing self-heal; idempotent, silent when nothing changes
  • _finalize_after_budget_exhausted: on turn-budget exhaustion, strips the tools and makes one more call so the model can summarize, rather than hard-stopping

8.2 session_store.py — persistence

  • load_history: faithful read (never rewrites data; self-healing belongs at the agent boundary)
  • repair_tool_pairing: bidirectional repair, returns stats (backfilled / dropped_orphans / dropped_duplicates / dropped_dangling)
  • Session lock: prevents two processes writing the same session and interleaving history
  • Dual FTS5 indexes (Chinese/English tokenisation) + tool_result_archive (folded originals)

8.3 compressor.py — context compression

  • L1 folding: long tool results truncated head+tail, originals archived (zero LLM cost)
  • L2 incremental summary: prior summary + new block → new summary; cut points land on user boundaries
  • Runs _validate_history afterwards and rolls back if invalid (compression must never be worse than none)
  • Circuit breaker: three consecutive failures pause the mechanism

8.4 turn_context.py / tool_guardrails.py

Neither executes actions or prints — both keep records only, so they are unit-testable without an LLM. But they differ in nature:

  • tool_guardrails.py issues verdicts (warn/block), because "spinning in place" is decidable from behavioural facts
  • turn_context.py states facts and issues no verdict — build_stop_context() renders "what changed, what ran, what the results looked like"

8.5 tools/registry.py — tool registry

  • Registry pattern: adding a tool means editing tools/__init__.py only
  • Hardened dispatch: exception fallback + result normalisation
  • Confirmation injection: copies the args before injecting _confirm (never mutates the caller's dict, which would desync the guardrail's before/after signature)
  • InterruptSignal passes through dispatch; core catches it and handles /p

9. Key Decisions

DecisionRationale
Business constraints self-heal at the agent boundary; the persistence layer stays a faithful reader Putting it in load_history breaks the faithful-read contract (empirically: it broke an existing test)
Confirmation semantics belong to the handler; /p interception belongs to core Each tool presents different content, but interrupt semantics must be globally consistent
Guardrails hard-stop by default (a deliberate divergence from Hermes' default-off) For a single-user interactive assistant the point is cutting losses; overridable via env var
Guardrails skip the "same tool regardless of args" signal Retries have legitimate uses; counting by tool name alone causes false positives
Verification tier A: evidence = one full green suite run A green suite implicitly covers the changed files, so no module→test mapping needs maintaining
On budget exhaustion, strip tools and summarize rather than hard-stop Dozens of turns of tool work should not yield only "stopped"
Add strictness on the evidence content axis, not by lowering thresholds The "judge" axis is already hard (exit codes are read directly)
History uses a single choke point (not atomic batches) See §6.4: mutually exclusive with Ctrl+C retention; decided on frequency × cost
No elaborate prompt-injection filtering Local single-user use; visibility plus a human at the terminal covers it

10. Known Limitations

10.1 Tool success/failure is still inferred from strings

is_tool_error has been fixed for its two directional bugs (success read as failure, cancelled read as success), but it still guesses at wording. The root-cause fix (structured fields) has completed research and design — see tool-result-structuring-design.md.

  • Residual: content that literally contains [错误] is misclassified (a test records this limitation)

10.2 Exit-code semantics are not distinguished

grep returning 1 for "no match" is normal, but the current predicate treats it as failure. Research found this to be a genuine gap in the literature — no dedicated study exists.

10.3 Other

  • No backup mechanism: session.db is a single point of failure; one bad DELETE is unrecoverable
  • The archive table only grows: folded originals have no pruning path (measured at 80 rows today, not urgent)
  • Soft criterion unmet: a half-batch briefly exists on disk (judged acceptable — see §6.4)
  • Not built: streaming output, multi-platform gateway
