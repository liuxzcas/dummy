1. Scope & Design Principles

Dummy Agent is a personal AI assistant built from scratch. The goal is not to replicate an existing framework, but to serve as an assistant that is genuinely used, improves with use, stays low-friction, can be trusted, and acts proactively.

Three non-negotiable principles

PrincipleMeaningWhere it shows up
Single choke point One entry per concern; cross-cutting concerns live behind one door _parse_tool_arguments (parsing), _make_confirm (confirmation), _append_user_turn (user messages), project_messages (outbound validity)
Visibility over filtering No elaborate sanitizing; local development relies on visibility plus a human at the terminal Every tool call and result is printed; the user decides via y/n
Honesty over polish What could not be verified is labelled as such; inference is never presented as evidence The "unverified", "known limitations", and "literature gap" sections throughout the docs
Relationship to the Phase 0 document
The Phase 0 design document is preserved at design-phase0.html (Chinese: design-phase0-zh.html). That document records what we deliberately chose not to build, and is intentionally left unedited — the history of a decision is itself valuable information. This document describes the current state.

Anatomy of a single chat()

chat(user_input)                         ← shell: try/finally guarantees history settlement
 └─ _chat_impl(user_input)
     ├─ _ensure_session()                 ← create session + acquire lock on first call
     ├─ inject: datetime / cwd / memories / skill index / lessons   ← all idempotent
     ├─ per-turn reset: guardrail counters, verification ledger
     └─ for turn in range(max_tool_turns):        ← default 40, configurable
          ├─ _maybe_compress()           ← compress past 70% of the context window
          ├─ project_messages(history)   ← project into valid messages (outbound choke point)
          ├─ llm.chat(...)
          └─ tool_calls present?
               ├─ yes → execute each (guardrail pre/post hooks, ledger bookkeeping)
               │        └─ batch end → check interrupts → persist
               └─ no  → verify gate: code changed but no evidence? → reject (≤2 times)
                        otherwise persist → return
     finally: _settle_history()          ← whatever the exit path, repair pairing and persist

5. Conversation History: Evolving a Single Source of Truth

This is the most winding thread in the project, and where most architecture effort went.

5.1 The problem

self.history is a shared mutable list that must satisfy four classes of invariant simultaneously: protocol validity (tool_calls↔tool pairing, role alternation), durability (lossless save/load), compressibility, and readability (guardrails and the verification gate read per-turn state). These four had no owner, so every component added its own fallback — five to seven patches for a single problem.

5.2 Root cause (established empirically)

Illegal state was actively written to disk.
The old implementation persisted inside the time window between assistant(tool_calls) and the remaining tool replies of the same batch. Exceptions, hard kills, and power loss were merely who triggered it, not the root cause.

5.3 Four-way measured comparison

The criteria fall into three groups: AR-chat (history must be valid on any exit through chat), AR-stop (disk must be valid after a mid-batch stop), and SOFT1 (soft criterion: illegal state never appears on disk — bonus, not a gate).

RouteAR-stopSOFT1SuiteVerdict
1 — Managed History classfailfail1 failure fail — end_tool_batch() is unreachable when the batch stops mid-flight (write time cannot see the future)
2 — Projectionfailfail1 failure fail — only covers the send side, never touches persist timing
3 — Single choke pointpassfail0 failures adopted — see below
5 — Atomic batchpasspass0 failures Technically best, but sacrifices Ctrl+C data retention — not adopted

5.4 Final design: single choke point (route 3)

try:
    return self._chat_impl(user_input)   # body: the tool loop
finally:
    self._settle_history()               # single exit: repair pairing + persist

Why not the "cleaner" route 5 — measurement showed the two are mutually exclusive with preserving completed tool results on Ctrl+C:

ApproachCompleted tool results on Ctrl+CHalf-batch briefly on disk
Route 3Preserved (measured on disk)Yes
Route 5Entire batch lostNever
Decision basis: Ctrl+C is a high-frequency operation (the whole interaction design is built around it and /p), and tools may be non-repeatable (builds, network, hardware) — losing results is a real cost. A half-batch briefly on disk is not a problem: the only read path, resume_session(), repairs it (7 of 7 shapes verified).

6. Quality Gates

GateTimingMechanism
P1a Tool guardrails Real time, inside the loop Two signals: the same failure repeating (same tool + args + identical failure output), and read-only calls making no progress (repeated result fingerprint). Warn on the 2nd, block on the 6th
P1b Verify-on-stop When the model tries to finish If code files changed this turn but no evidence of a full test-suite pass exists → reject (max 2). Evidence must postdate the last edit
P2b History hygiene Entry / throat / exit Bidirectional pairing repair (backfill missing / drop orphans / dedupe / drop trailing dangling block) plus role-alternation fallback

Why the guardrail requires "identical failure output"

Counting by tool + args alone flags the normal edit-run-edit cycle (same command, different error each time) as spinning and blocks it — while the verification gate requires that command to pass. The two deadlock. Measured outcome: two rejections, then finishing with "no evidence + claims complete" — precisely what the gate exists to prevent.

Evidence definition (tier A)

  • Must be a full test-suite pytest run that succeeded
  • Must end with the pytest invocation — a pipe masks the exit code (pytest | tail returns tail's 0)
  • Must have actually executed (result carries [SHELL:, ruling out "user cancelled")
  • Documentation extensions are exempt

7. Module Reference

7.1 core.py — the tool loop

  • _parse_tool_arguments: three-tier tolerance (json → json5 → regex + unescape)
  • _append_user_turn: the single entry for user messages, doubling as the role-alternation fallback; synthetic messages carry _meta.synthetic so compression does not count them toward "keep last N turns"
  • _repair_history: pairing self-heal; idempotent, silent when nothing changes
  • _finalize_after_budget_exhausted: on turn-budget exhaustion, strips the tools and makes one more call so the model can summarize, rather than hard-stopping

7.2 session_store.py — persistence

  • load_history: faithful read (never rewrites data; self-healing belongs at the agent boundary)
  • repair_tool_pairing: bidirectional repair, returns stats (backfilled / dropped_orphans / dropped_duplicates / dropped_dangling)
  • Session lock: prevents two processes writing the same session and interleaving history
  • Dual FTS5 indexes (Chinese/English tokenisation) + tool_result_archive (folded originals)

7.3 compressor.py — context compression

  • L1 folding: long tool results truncated head+tail, originals archived (zero LLM cost)
  • L2 incremental summary: prior summary + new block → new summary; cut points land on user boundaries
  • Runs _validate_history afterwards and rolls back if invalid (compression must never be worse than none)
  • Circuit breaker: three consecutive failures pause the mechanism

7.4 verify_stop.py / tool_guardrails.py

Both are pure controllers: they only keep records and return verdicts — no side effects, no printing — which makes them unit-testable without an LLM.

7.5 tools/registry.py — tool registry

  • Registry pattern: adding a tool means editing tools/__init__.py only
  • Hardened dispatch: exception fallback + result normalisation
  • Confirmation injection: copies the args before injecting _confirm (never mutates the caller's dict, which would desync the guardrail's before/after signature)
  • InterruptSignal passes through dispatch; core catches it and handles /p

8. Key Decisions

DecisionRationale
Business constraints self-heal at the agent boundary; the persistence layer stays a faithful reader Putting it in load_history breaks the faithful-read contract (empirically: it broke an existing test)
Confirmation semantics belong to the handler; /p interception belongs to core Each tool presents different content, but interrupt semantics must be globally consistent
Guardrails hard-stop by default (a deliberate divergence from Hermes' default-off) For a single-user interactive assistant the point is cutting losses; overridable via env var
Guardrails skip the "same tool regardless of args" signal Retries have legitimate uses; counting by tool name alone causes false positives
Verification tier A: evidence = one full green suite run A green suite implicitly covers the changed files, so no module→test mapping needs maintaining
On budget exhaustion, strip tools and summarize rather than hard-stop Dozens of turns of tool work should not yield only "stopped"
Add strictness on the evidence content axis, not by lowering thresholds The "judge" axis is already hard (exit codes are read directly)
History uses a single choke point (not atomic batches) See §5.4: mutually exclusive with Ctrl+C retention; decided on frequency × cost
No elaborate prompt-injection filtering Local single-user use; visibility plus a human at the terminal covers it

9. Known Limitations

9.1 Tool success/failure is still inferred from strings

is_tool_error has been fixed for its two directional bugs (success read as failure, cancelled read as success), but it still guesses at wording. The root-cause fix (structured fields) has completed research and design — see tool-result-structuring-design.md.

  • Residual: content that literally contains [错误] is misclassified (a test records this limitation)

9.2 Exit-code semantics are not distinguished

grep returning 1 for "no match" is normal, but the current predicate treats it as failure. Research found this to be a genuine gap in the literature — no dedicated study exists.

9.3 Other

  • No backup mechanism: session.db is a single point of failure; one bad DELETE is unrecoverable
  • The archive table only grows: folded originals have no pruning path (measured at 80 rows today, not urgent)
  • Soft criterion unmet: a half-batch briefly exists on disk (judged acceptable — see §5.4)
  • Not built: streaming output, multi-platform gateway
