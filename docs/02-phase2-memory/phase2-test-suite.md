# Phase 2 综合测试集 — 设计与结果

> 状态:已完成(2026-08-12)
> 目标:覆盖整个 Phase 2 的 comprehensive test cases——持久化 + 压缩 +
> 全文搜索 + 跨 Session 记忆,分层执行,给出可信的"Phase 2 整体验收"。
> 执行:五层套件全部落地,T5 最终成绩 28/30 = 93%(演进记录见 §10)。

> EN TL;DR: Phase 2 integrated test suite. Five tiers: T1 persistence,
> T2 compression (existing 30-unit + 8-quest quality gate + 25-round smoke),
> T3 FTS search, T4 cross-session memory, T5 LongMemEval-style regression
> (20-30 real-model questions, 5 task types). Tiers 1/2-unit run on mocks
> (fast, deterministic); tier 5 uses real DeepSeek (~¥0.5 per run).
> Verdicts: norm() whitespace-insensitive + multi-expectation all() checks.

## 1. 测试哲学(为什么这样设计)

1. **失败模式驱动**:每条断言对应一个具体失败模式(某个设计决策错了会怎样),
   不是"证明功能存在"
2. **分层隔离模型能力**:系统功能(单元/集成)用 mock——零成本、零污染,
   测的是"我们的代码"不是"模型的临场发挥";端到端(冒烟/回归集)用真实
   模型——测"生产配置下的整体行为"。两层结论不可互相替代
3. **断言语义严格对齐**:判定统一 norm()(去空白+小写)+ 多期望列表 + all()
   ——空白差异是测量噪音,漏答任何期望都是失败(质量门 Q6 踩过的坑)
4. **验证结果不提交**:逐题明细留在会话内,仓库只保留测试代码本身

## 7. T5 LongMemEval 回归集(20-30 题,真实模型)

**来源**:LongMemEval(arXiv:2410.10813,500 题,5 类任务,记忆系统事实上的
评测标准)的五类任务,转成 dummy-agent 场景的 20-30 题。

**题目结构(每题)**:
```
构造:一段 10-25 轮对话,埋入 2-4 个事实(偏好/项目决策/关键配置)
恢复:新会话(或压缩后),注入记忆/FTS 检索生效
提问:按题型提问
判定:norm() 去空白 + 多期望列表 + all()(与质量门一致)
```

**五类题型 × 内容**:

| 题型 | 测什么 | 例 | 依赖的能力 |
|------|--------|----|-----------|
| 1. Long-context QA 长上下文问答 | 跨多段信息整合 | "把两段对话里提到的部署方案合并起来是什么?" | 记忆注入 + 历史 |
| 2. Statistic QA 统计问答 | 计数/频率 | "用户一共改过几次测试框架?"(埋 2 次偏好变更) | 记忆冲突覆盖链 |
| 3. Post-hoc QA 事后问答 | 最终状态 | "对话结束时项目部署在哪个环境?" | 记忆覆盖(新覆盖旧) |
| 4. Conversation QA 对话问答 | 具体说了什么 | "用户在第 7 轮说的端口号是多少?" | **FTS 检索**(2.3b) |
| 5. Personal QA 个人信息 | 长期偏好 | "用户偏好什么语言/工作习惯?" | 记忆注入(2.4) |

每类 4-6 题,重点:**题型 4 必须依赖 FTS 检索**(对话历史太长,记忆抽取
可能略过细节——这题验证 2.3b 检索链),**题型 5 必须依赖记忆注入**
(事实在别的 session,当前对话从未出现过——验证 2.4 跨会话能力)。
两道"必须依赖"是回归集的命门:如果 FTS/记忆被拆掉,对应题型应整组失败。

**执行**:scripts/phase2_regression.py——逐题:构造对话(临时库)→ 对话
(真实模型)→ 新会话提问 → 判定 → 输出逐题 ✅/❌ + 汇总(通过率/失败
原因分类)。预计 30 题 ≈ 15-20 分钟,~0.5 元。

### 验证方法要点(从执行中沉淀)

1. 失败模式驱动:每条断言对应一个设计决策的失败形态
2. 判定严格对齐:norm(去空白 + 中文数字归一化)+ 多期望 all()
   ——"三个" vs "3" 是测量噪音,必须归一化
3. 测试数据模拟真实形态:折叠后消息 + 归档原文(中间信息)分离,
   才能证明"只有归档表搜得到"
4. 每题目独立 db:共享 db 时前题记忆污染注入检索(实测踩坑)
5. 验证脚本自身也会错:断言与设计决策语义对齐,区分代码 bug 与测试 bug

### 剩余失败模式(T5 最终轮 2 题)

- conversation 数据库名(21):抽取/提炼词随机波动(兜底本可救)
- personal 工作习惯(29):同义词鸿沟——提炼词"工作习惯"与历史文本
  "先看文档"无字面重叠,关键词检索的终极边界(向量是演进方向)
