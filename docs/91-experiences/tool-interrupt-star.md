# 工具打断功能开发复盘 — STAR 法则总结

> 项目:dummy-agent
> 日期:2026-08-14
> 主题:**前期构思不成熟 → 后期改动牵一发而动全身**的典型工程实践应对

---

## 一、功能背景与开发过程(完整回顾)

### 需求起点

在 tool_calling loop 中加入"随时打断 + 听用户意见":
1. 暂停循环(等当前工具执行完,不再跑下一个 tool call)
2. 用户能在断点输入提示词
3. 提示词作为 user 消息进入下一轮,LLM 重新规划

用户初步想法:`/p xxxx` 行内带提示词。

### 设计演进(五轮收敛)

| 轮 | 方案 | 走向 |
|----|------|------|
| 1 | 工具确认处解析 `/p xxxx` | 用户想法,断点 = 确认处 |
| 2 | 升级"任何时间"打断 | 非阻塞监听(msvcrt 轮询 + 检查点) |
| 3 | 只改 core.py 降耦合 | 确认仍在工具内,代价:确认处 /p 丢失 |
| 4 | 确认统一归 core 管理 | 工具纯函数化,但丢失 write_file diff 细节 |
| 5(定稿) | **确认语义归 handler + /p 拦截归 core** | 注入 `_confirm` 函数:handler 展示确认内容(y/n/d 等),core 做输入收集 + /p 拦截(InterruptSignal 穿透) |

### 实施与真机迭代(四轮)

- **分支 confirm-interrupt**:InterruptSignal 无参触发 + dispatch 显式穿透 + 三防线(穿透 / 确认前置零副作用 / 幂等守卫)
- **真机第一轮**:write_file 用 line 模式时无确认直接改文件;工具运行中输入无回显;`/p` 提示没出现 → 修复:全模式确认 + 后台线程实时回显 + 提示文案
- **真机第二轮**:两次输入粘连(take_line 与监听线程并发竞态)→ threading.Lock 修复
- **设计调整**:`/p` 改纯触发(后缀忽略、无回显),打断后统一在打断处理点收集提示词,空提示词 = 取消打断
- **真机第三轮**:验证通过,但分支多轮 patch + 字节级修复,污染风险 → **干净重建**
- **干净重建**:从 main 全新 fork,6 个文件全新写入,逻辑 diff 确认一致,真机第四轮验证通过 → 合并 main

### 过程中的坑

1. **patch 工具 `\r` 转义陷阱**:new_string 里的 `\r` 被转成真实字节破坏源码,反复踩坑 4 次——最终用 chr(13)/chr(10) 规避,干净重建时彻底绕开
2. **cua-driver 故障**:无法驱动真实桌面,PTY 模拟 stdin 交互不可靠、bash 直连被墙需代理——最终由用户手动真机测试
3. **测试脚本自身 bug 多次**:mock 恒返回值误判、路径外确认抢输入序列、input prompt 不走 stdout——靠"断言与设计语义对齐"排查

## 二、STAR 法则总结

### S — Situation(情境)

用户提出"打断 + 提示"功能,核心诉求本身很简单(暂停循环 / 断点输入提示词 / 提示词进下一轮)。但**前期设计探讨聚焦在"功能怎么做",没有先锁定"架构归属"**——确认交互归谁、打断信号如何跨层传播、哪些层需要动。结果:每次需求细化(任何时间打断 → 隐藏输入 → 纯触发)都牵动 core + registry + 多个 handler,修改面反复扩散,经历了"实现 → 真机发现问题 → 修复 → 再发现问题"的多轮循环。

### T — Task(任务)

在最小改动、可演进的前提下落地该功能,并确保后续需求变化(随时打断、无回显、纯触发、空提示词取消)不被初始架构拖累;同时保证可验证(定向测试 + 真机)与可回退。

### A — Action(行动)

针对"牵一发而动全身",采取了一套组合策略:

1. **先定架构归属,再写代码** — 明确"交互与执行分离":确认**语义**归 handler(每种工具展示自己的确认内容),输入**收集与 /p 拦截**归 core(注入 `_confirm` 函数)。职责边界清晰后,后续改动只动归属方。

2. **信号通道先行** — 打断用 `InterruptSignal` 专用异常 + dispatch 显式穿透(不依赖字符串约定,不被异常兜底吞掉)。信号传播通道从第一天就固定,后面加路径(检查点 / 确认处)只是往通道上接。

3. **单点汇聚** — 所有打断路径(确认处 InterruptSignal、检查点监听)汇合到**一个处理点**(统一收集提示词)。后续"空提示词取消""统一问提示词"都只改这一处。

4. **接口向后兼容** — handler 的 `_confirm=None` 可选参数:直接调用 / 测试时跳过确认,新调用方式(dispatch 注入)与旧方式并存,降低迁移成本。

5. **零副作用约定** — 确认前置:handler 所有副作用严格排在确认之后,打断发生时没有需要回滚的状态。

6. **干净重建优于打补丁** — 多轮 patch + 字节级修复后代码风险累积(看不见的杂质),从 main 全新 fork 重写 6 个文件,逻辑 diff 验证一致,彻底消除污染顾虑。

7. **测试先行于真机** — 每轮改动先定向验证(mock 输入按 prompt 内容路由)+ pytest 回归,真机只验真机特有项(msvcrt 监听 / 回显),把试错成本压在自动化侧。

### R — Result(结果)

- 功能最终落地并合并 main,4 轮真机验证全部通过(确认 / 打断 / 提示词注入 / 取消)
- 后续小改动(write_file 确认改 while 重试、`/sessions del`、`/history del`)都只动单层,不再牵一发而动全身
- 验证体系沉淀:40+ 项定向验证 + pytest 72 项全绿
- 经验文档化(本文),"先定归属 → 信号通道 → 单点汇聚"成为后续功能开发的模板

## 三、通用可复用策略详解

以下策略从本次开发中抽象,适用于任何"新功能需求 + 后续需求会变"的工程情景。每条给出:适用场景 / 怎么做 / 为什么。

### 策略 1:动手前锁定"架构归属"——归属三问

**适用场景**:任何涉及多层协作的新功能(交互、执行、存储、信号传播)。

**怎么做**:写代码前用 1-2 轮设计讨论回答三个问题:

```
Q1 职责边界:这个功能拆成几层?每层负责什么?
   —— 判断归属的判据:信息谁最自然拥有?
      · 展示/语义内容(确认文案、diff 展示)→ 归拥有该信息的层(handler)
      · 全局一致规则(/p 拦截、输入收集)→ 归公共层(core)
      · 案例:确认文案各工具不同 → handler;打断拦截所有工具一致 → core

Q2 信号通道:跨层数据/控制流怎么传?用什么载体?
   —— 通道先行并固定:专用异常 / 回调注入 / 事件,不用字符串约定
   —— 案例:InterruptSignal 专用异常 + dispatch 显式穿透

Q3 会变的需求点:哪些地方最可能改?为它们预留扩展位
   —— 高频变化的三类:交互形态(确认选项)、展示内容(文案/diff)、
      触发协议(/p 格式)。算法与存储相对稳定,不必过度设计
   —— 案例:/p 从行内提示词 → 纯触发,靠"触发与提示词解耦"只改一处
```

**为什么**:本次五轮设计收敛,前三轮都在补归属的课(交互在工具里?在 core 里?信号怎么传?)。职责不清时,任何需求变化都同时波及多层——这是"牵一发而动全身"的直接成因。

### 策略 2:识别"高频变化点"并解耦

**适用场景**:交互型功能(任何面向用户的输入/确认/指令协议)。

**怎么做**:把"触发"与"内容"分离、把"交互语义"与"交互收集"分离:

```
变化维度        稳定维度
─────────      ─────────
触发协议(/p)    打断后的处理流程
确认选项(y/n/d)  输入收集 + /p 拦截
展示内容(diff)   信号传播通道
```

**为什么**:本次 `/p xxxx` → `/p` 纯触发、回显 → 无回显、确认前加 while 重试,三次需求变化都只动了变化维度(触发解析、显示),稳定维度(InterruptSignal 通道、打断处理点)零改动。若当初把触发协议耦合进处理流程,每次都要重写处理逻辑。

### 策略 3:信号通道先行并固定(单一职责的传播层)

**适用场景**:跨层控制流(中断、取消、错误传播)。

**怎么做**:

```
1. 用专用异常/回调/事件承载信号,不用返回值约定或字符串标记
   —— 字符串标记会被普通数据流吞掉、无法区分;异常有类型可识别
2. 信号必须穿透的所有兜底层,显式声明 re-raise
   —— 案例:dispatch 的 except InterruptSignal: raise
   —— 否则信号被"异常兜底"吞成一条错误消息,失效且难排查
3. 通道建立后,新增信号来源只是"接入通道",不改通道本身
   —— 案例:确认处 InterruptSignal + 检查点监听,两条路径汇合
```

**为什么**:本次 InterruptSignal 从第一天就固定为"专用异常 + dispatch 穿透",后面加检查点路径、改纯触发、加空提示词取消,都只是接入/处理层变化,通道本身零改动。

### 策略 4:单点汇聚——所有路径汇合一个处理点

**适用场景**:同一事件有多个来源(用户输入、异步监听、回调)。

**怎么做**:

```
1. 所有来源 → 同一处理点(一个函数/一个代码块)
2. 后续行为变化(加取消、改提示词收集)只改这一个点
3. 幂等守卫放在汇聚点(同一轮只处理一次)
   —— 案例:interrupt_triggered 标志,两条打断路径不会重复注入
```

**为什么**:本次"确认处 /p"和"检查点 /p"最初是两套处理,真机测试暴露拼接/双注入问题后才收敛为单点。单点汇聚后,"空提示词取消""统一问提示词"都是一行改动。

### 策略 5:接口向后兼容(新增参数带默认值)

**适用场景**:被多方调用的函数/组件(handler 被 LLM 循环、测试、直接调用)。

**怎么做**:

```
- 新增能力用可选参数,默认值 = 旧行为
  —— 案例:handler 签名加 _confirm=None,直接调用/测试跳过确认,
    dispatch 注入时启用确认——三态兼容(旧调用/新调用/测试)
- 纯函数 + 可选交互参数:交互能力是"注入的",不是函数自带的
```

**为什么**:handler 从"内部 input"迁移到"注入 _confirm"时,如果没有默认值,所有旧调用点(测试、直接使用)全部要改。可选参数让迁移成本≈0,且测试可以无交互地跑纯逻辑。

### 策略 6:副作用严格后置(可中断点之前零状态变更)

**适用场景**:任何支持中断/取消/审批的流程(工具执行、批处理、多步写入)。

**怎么做**:

```
1. 确认/审批类交互排在所有副作用之前
2. 副作用之前只允许纯计算(生成预览、校验参数)
3. 若确认后需持有资源,用 try/finally 保证打断时清理
   —— 案例:write_file 的 diff 计算/路径检查在确认前,
    文件写入在确认后;打断发生时没有需要回滚的状态
```

**为什么**:中断发生在副作用之前 = 没有半途状态需要处理。本次设计讨论中预判了"确认中打断"的五种错误场景(信号被吞/半途副作用/资源泄漏/双注入/处理点分散),"零副作用"是从源头消除其中最危险的一类。

### 策略 7:验证分层——自动化先于真机

**适用场景**:功能含环境特有行为(console 监听、键盘回显、真实 I/O)。

**怎么做**:

```
1. 自动化能覆盖的(行为语义)→ 定向测试
   —— mock 输入按 prompt 内容路由,覆盖确认/打断/注入/取消全路径
2. 环境特有的(msvcrt 监听、回显、真实 API)→ 真机
3. 每轮改动:先自动化回归,再真机抽查;试错成本压在自动化侧
4. 测试脚本自身也会错:
   —— mock 恒返回值导致误判(用 side_effect 序列/按内容路由)
   —— 无关代码抢输入序列(测试目标放对位置)
   —— input prompt 不走 stdout(用 mock 记录 call_args 而非捕获输出)
   —— 判定"代码 bug vs 测试 bug":断言与设计语义对齐
```

**为什么**:本次每轮修复都先跑定向验证(累计 40+ 项)再上真机,真机只暴露真机特有项(回显、粘连);测试脚本自身踩了 3 次坑,每次都用"语义对齐"快速定位,没有浪费真机轮次。

### 策略 8:干净重建的决策阈值

**适用场景**:同一区域经历多轮修补后。

**怎么做**:

```
1. 识别失控信号:
   —— 同一文件/函数被 patch 修补 3+ 次
   —— 出现字节级修复(转义、编码层面打补丁)
   —— 存在"无法解释的杂质"(注释混字符、行尾不一致)
2. 决策:重建成本 = 重写文件 + 逻辑 diff 验证;继续修补成本 =
   每轮补丁 + 污染风险累积 + 排查杂质的时间
   —— 一旦修补次数超过阈值,重建是更便宜的选项
3. 执行方式:
   —— 从干净基线(main)fork 新分支,文件全新写入
   —— 与旧分支做逻辑 diff(过滤注释/空行后对比关键逻辑),确认一致
   —— 完整验证链重跑(定向 + 套件 + 真机)
   —— 旧分支保留作对照,验证通过后删除
```

**为什么**:本次 confirm-interrupt 分支经历 5 次提交 + 4 次字节级修复后,用户主动提出重建。重建后的代码与旧分支逻辑 diff 完全一致,但消除了所有历史杂质——这是"沉没成本"决策的典型场景:过去的修补时间不该成为继续打补丁的理由。

### 策略 9:变更记录与复盘文档化

**适用场景**:复杂功能收尾后。

**怎么做**:

```
1. 设计决策记录"为什么"(当时为什么这样选,备后来者理解)
2. STAR 复盘写入项目内 docs/experiences/,可被后续会话检索复用
3. 复盘聚焦"可迁移的教训"(职责归属/信号通道/单点汇聚),
   不只记录"发生了什么"
```

**为什么**:本次核心经验(归属三问、通道先行、单点汇聚)如果不落文档,下次新功能会重新踩"职责未分离"的坑。文档化的价值在于把一次性的试错成本变成可复用的工程准则。

## 四、核心教训(通用化)

1. **"牵一发而动全身"的根源不是需求变,而是职责没有在开始时分离清楚**——交互、执行、信号传播混在同一层时,任何需求变化都同时波及多层。检测方法:一次需求变化需要动几层?超过 2 层就该回查归属。

2. **架构归属的决定要趁早**——前期 1-2 轮对话定归属,远小于后期每轮改动都动多层的成本。本次五轮设计收敛,前三轮都在补归属的课;若一开始就执行"归属三问",可省两轮。

3. **具体归具体层,规则归规则层**——展示/语义内容(确认文案、diff)归拥有信息的层;全局一致的规则(/p 拦截、输入收集)归公共层。这是归属判断的通用判据。

4. **修补次数超过阈值时,干净重建是更便宜的选项**——保留旧分支对照,逻辑 diff 验证一致性,别让沉没成本决定继续打补丁。

5. **测试脚本本身会错,断言必须与设计语义对齐**——mock 行为、捕获方式、数据准备都可能引入假失败;区分"代码 bug"与"测试 bug"是调试的第一步。

## 五、补救之道:接受不完美,投资补救能力

> 本文前三节讲"如何预防"(归属三问、通道先行、单点汇聚),本节讲一个更现实的前提:**预防的优先级并不高**。
>
> 越是花心思预防"牵一发而动全身",前期开发阶段就越畏首畏尾——为了覆盖所有可能的后续变化而做的设计,大部分永远不会被用到;顾虑太多反而拖慢进度,而进度本身就是早期最大的风险(需求可能变、方向可能错、技术可能不适用)。

### 5.1 为什么预防优先级低

```
1. 预防的收益是概率性的:设计再周全,也猜不到真实需求变化
   —— 本次五轮设计收敛,前三轮是"补归属的课",但真正让方案
     定型的,是第四轮真机测试暴露的问题,不是前期设计
2. 预防的成本是确定性的:每多一层抽象/扩展位,都是当前的
   理解成本 + 实现成本 + 维护成本
3. 过度设计会反噬:预留的扩展位若与真实需求不符,反而成为
   新需求的障碍(要绕开它或重写它)
4. 工程实践规律:问题在真实使用中暴露得最快、最准
   —— 真机一轮暴露的问题,抵得上十轮纸上推演
```

结论:**前期只做最低成本的预防**(归属三问这类一轮对话能定的),其余交给补救能力。

### 5.2 补救能力的四大支柱

补救能力 = 出了问题能快速、低成本地修正。四个支柱,按投入产出排序:

**支柱 1:回退点(补救的地基)**

```
做法:
- 每个阶段有明确回退点:干净的提交 + 分支/标签
- 改动前确保"改坏了能回到哪"
- 实验性改动放独立分支,主线保持可运行

本次案例:
- hermes-memory-v3 / plugmem-v2 分支实验,main 始终可运行
- confirm-interrupt 多轮修补失控后,旧分支保留作对照
- 用户决策"先试,不行退回原版本"——回退点是敢试的前提
```

**支柱 2:验证网(补救的眼睛)**

```
做法:
- 自动化测试覆盖核心行为(问题一出现就被抓住)
- 分层验证:定向测试(行为语义)→ 套件回归 → 真机(环境特有)
- 测试脚本自身也要可纠错(断言与设计语义对齐)

本次案例:
- 累计 40+ 项定向验证 + pytest 72 项,每轮改动后先跑
- 真机 4 轮,每轮暴露 1-3 个问题,全部被快速定位修复
- 验证网的价值:不是"证明没 bug",而是"bug 出现时 5 分钟内发现"
```

**支柱 3:小步快跑(补救的成本控制)**

```
做法:
- 一次只改一小块,改完立即验证,不攒大改动
- 问题范围小 → 定位快 → 补救成本低
- 宁可多几轮小迭代,不追求一步到位

本次案例:
- 每轮真机后只修该轮暴露的问题(全模式确认 / 回显 / 加锁),
  不顺手改无关代码
- 设计调整(/p 纯触发)也是一次一个变化点
```

**支柱 4:干净重建(补救的终极手段)**

```
做法:
- 当修补成本超过重建成本时,果断重建(见策略 8)
- 保留旧分支对照,逻辑 diff 验证一致性
- 重建不是失败,是"换一种更便宜的修法"

本次案例:
- confirm-interrupt 5 次提交 + 4 次字节级修复后,用户主动提出
  从 main 重建——重建后 18 项定向 + 72 项套件一次全绿
```

### 5.3 补救的时机判断

```
打补丁 vs 重建,用成本说话:

继续打补丁的成本 = 本次补丁工作量 + 污染风险(累积) + 排查杂质时间
干净重建的成本     = 重写文件 + 逻辑 diff 验证 + 全套验证重跑

判断信号:
- 同一区域修补 ≥3 次 → 评估重建
- 出现字节级修复(转义/编码层面)→ 强烈建议重建
- 修复后仍要反复看同一段代码 → 说明结构不清,重建优于再补
```

### 5.4 预防与补救的平衡(最终建议)

```
预防只做三件事(成本极低,一轮对话内):
1. 归属三问(职责边界 / 信号通道 / 会变的需求点)
2. 通道先行(跨层信号用专用异常/回调,不用字符串约定)
3. 回退点(分支/提交干净,敢试的前提)

其余全部交给补救:
- 大胆快速推进,接受"设计不周会来"
- 验证网兜底(问题快速暴露)
- 小步快跑(问题范围小)
- 修补失控时重建(终极手段)

心态:补救是正常流程,不是失败。
"先跑起来,再补课"——跑起来才有真实反馈,补课才有方向。
```
