# 残留进程报告：机制、覆盖范围与已排除的方案

> 编写时间：2026-10-16
> 相关代码：`tools/tasks.py`、`tools/terminal.py`
> 相关测试：`tests/test_task_reporting.py`

---

## 一、要解决的问题

**场景**：模型执行一条命令，命令退出后**还留下了后台进程**（例如 `npm run dev &`、`nohup server.py &`）。

**该做什么**？两个层次，必须分开：

| 层次 | 谁负责 | 做什么 |
|---|---|---|
| **机制** | 代码（script 流程） | 超时后**杀**整棵树 —— 不问 LLM（不杀就泄漏） |
| **信息** | 代码收集、**模型判断** | 报告"还留着哪些进程" —— 代码不替模型决定要不要杀 |

**为什么"要不要杀"归模型**：

```
用户可能故意启动了一个常驻服务(pm2 / dev server)
    → 代码不知道意图,不该替模型做决定
所以只报事实:"命令 X 起的进程还在跑,pid=1234,已运行 3 分钟"
```

## 二、实现（`tools/tasks.py`）

### 2.1 进程登记表

```python
@dataclass
class TaskRecord:
    pid: int                    # 根进程 pid(通常是 bash)
    command: str                # 命令原文 —— 报告时让模型知道"哪条命令留下的"
    started_at: float
    status: str                 # running | done | killed
    descendants: list[int]      # 探查到的后代 pid(兜底名单)
```

**为什么是"表"不是"树"**：dummy 的进程关系是扁平的（一次工具调用 → 一棵进程树），
各次调用之间没有父子关系。需要"树"的场景是子 Agent 委派（Phase 4）。

**内存版，不落盘**（用户定的）：覆盖"退出时清理"这个实际场景即可；
覆盖"dummy 被强杀后的残留"需要落盘 + 处理 pid 复用，风险收益比不高。

### 2.2 报告文案

`format_lingering_report(records) -> str` —— **只陈述事实，不含指令**：

```
[提示] 上面这条命令还留下了仍在运行的进程(不是错误,只是事实):
  · 命令 'npm run dev' 启动的进程仍在运行: pid=12345,已运行 3 分 20 秒
```

**没有残留时返回空串**（不制造噪音、不白耗 token）。

### 2.3 接线点

报告加在 `terminal_handler` 的返回处（**不是** core 的工具循环）——
因为只有 terminal 会启动进程，归属清晰。

## 三、覆盖范围（实测）

### 能做到的

| 场景 | 能报告吗 | 说明 |
|---|---|---|
| 前台命令的进程树（命令仍在跑） | ✅ | shell 活着，PPID 链完整 |
| 超时被杀的树 | ✅ | 杀之前探查过 |

### **做不到的（已知局限）**

| 场景 | 原因 |
|---|---|
| **`cmd &` 后台进程** | ❌ **被过继**，PPID 链断 |
| **`nohup` 后台服务** | ❌ 同上 |

**实测证据**（2026-10-16）：

```
命令: sleep 30 & echo started

我们的 bash pid = 27072（已死）
从它递归探查 → 0 个后代
而 sleep 的 ppid = 28996   ← **不是** 27072!

→ sleep 被过继给了系统里【别的 bash】
→ 从我们启动的 shell 出发,永远找不到它
```

**另发现的时间窗口问题**（实测）：

```
t+ 551ms  bash 活着  → 探查到 4 个后代 ✅
t+1282ms  bash 已退出 → 探查到 0 个      ❌
窗口只有几百毫秒
```

**所以探查时机提前到了"shell 刚起来时"**（详见 `_run_shell` 里的轮询逻辑）。

## 四、已排除的两条路（避免以后重走）

### 4.1 管道信号 —— ❌ 无判别力

**初始假设**：后台进程攥着 stdout 管道 → `communicate` 等不到 EOF → 超时，
所以"管道未关闭"可以作为"还有进程在跑"的信号。

**实测结果（2026-10-16）**：

| 场景 | PeekNamedPipe | 读线程读到 EOF |
|---|---|---|
| 普通命令 `echo hello` | eof | True |
| 普通命令多行输出 | eof | True |
| **后台命令 `sleep 30 &`** | **eof** | **True** ← 正例也判成 eof |
| **`nohup` 后台服务** | **eof** | **True** ← 同上 |
| 前台长命令（被杀） | eof | True |

**全部无法区分** —— git-bash 在退出前会关闭/重定向 stdout，
父进程侧看到的就是 EOF。**初始假设是错的。**

### 4.2 快照差集 —— ⚠️ 能捞到，但有误报 + 代价高

**思路**：命令执行前后各拍一张全进程快照，差集就是"这次新起的进程"。

**实测结果（2026-10-16）**：

| 场景 | 差集 | 仍活着 | 捞到的进程 | 判定 |
|---|---|---|---|---|
| 普通命令 `echo hello` | 1 | 0 | — | ✅ 不误报 |
| 普通命令 `ls \| head -3` | 2 | 1 | **chrome.exe** | ❌ **误报** |
| 后台命令 `sleep 30 &` | 2 | 1 | sleep.exe | ✅ 正确 |
| `nohup` 服务 | 2 | 1 | sleep.exe | ✅ 正确 |
| 前台长命令（被杀） | 1 | 0 | — | ✅ 不误报 |
| 两个后台进程 | 3 | 2 | sleep.exe ×2 | ✅ 正确 |

**问题**：

```
① 误报无法根治 —— 两次快照之间【全系统】任何新进程都会进差集
   (实测 chrome 恰好在那 1 秒起子进程,就被当成"我们的残留")
   缓解手段都是启发式且不可靠:
     · 按命令行特征过滤 → nohup/daemon 常改命令行
     · 按"父进程也在差集里"过滤 → 被过继的进程父进程不在差集里(正是要捞的)

② 代价:每条命令 +1.05 秒(两次 PowerShell 快照各 0.52s)

③ 更隐蔽的代价:**误报会摧毁提示的可信度** ——
   模型看到"你有残留"但实际是 chrome,下次就不信这个提示了
```

## 五、当前决策

**做 B（只报探测到的）+ 如实记录局限。**

理由：

```
① B 已经实现,且**不误报**(探不到就不报,不编造)

```

**如果将来真的观测到需求** → 再评估 C，并且可以考虑收敛策略
（例如只报快照差集里"名字像服务"的进程）。

## 六、顺带修掉的一个真 bug

`note_descendants` 原实现是**覆盖式**：

```python
rec.descendants = list_descendants(rec.pid)      # 每次都覆盖
```

在"轮询探查"的用法下会丢结果：

```
第 1 次探:shell 活着  → 探到 3 个,写入 ✅
第 2 次探:shell 已退出 → 探到 0 个,**覆盖成空** ❌
```

**实测现象正是如此**：第一次调用返回 3 个 pid，最终 `descendants` 却是 `[]`。

**已改为累加式**（取并集，探查异常也不清空已有结果），
并有 4 条测试锁住（`TestDescendantsAccumulate`）。
