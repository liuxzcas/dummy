# 历史层架构方案对照实验 — 结论

日期:2026-09-16 | 分支:`arch/history-settle` / `arch/history-projected` / `arch/history-atomic`

## 0. 一句话结论

**路线 5(原子批次)胜出**:唯一同时通过硬标准与软标准的方案(208 全绿),
且改动最小(只挪 2 处落库时机,不新增任何兜底)。
**路线 2(投影器)是它的互补件**,不是竞争项——一个管落库侧,一个管发送侧。

## 1. 问题的重新认识(实验过程中修正了三次)

最初的目标是"把 5~7 处兜底收敛掉",过程中对问题本身的认识被纠正了三次:

| 阶段 | 当时的认识 | 被什么推翻 |
|---|---|---|
| 起 | "危险时刻"的入口很多(异常/Ctrl+C/强杀/断电) | 探针实测:经 chat 的异常路径**已被现有机制兜住** |
| 中 | 问题在于"什么时候修最合适" | 探针实测:**磁盘上真的躺过半个批次**(main 分支 4 条历史,结尾悬空) |
| 终 | **问题在于"非法状态被允许落库"** | `_persist_history()` 在每条 tool 结果后都调 —— 非法状态是**被主动写进磁盘的** |

**根因陈述**:`assistant(tool_calls)` 与"同批全部 tool 回复"之间有一个时间窗,
旧实现在这个窗口内就落库了。能让进程停在该窗口的原因(异常/强杀/断电)只是
"谁来触发",不是根因;根因是**窗口被暴露给了磁盘**。

## 2. 判据的三次校正(方法论记录)

判据本身就是实验的主要产出之一,它的三次校正值得单独记:

| 版本 | 问题 | 校正 |
|---|---|---|
| v1 | 只有 AR1(直接 `save→load`) | 它绕开 `chat()`,对"收口类"方案无从判定 → 拆出 AR-chat |
| v2 | AR-store 被当作验收标准 | 真实系统里历史**唯一写入者是 chat()**,"外部直接 save"是假问题 → 降为参考项,新增 AR-stop |
| v3 | 只看"停机后最终状态" | 无法区分"事后修"与"不让发生" → 新增 SOFT1(落库快照探针) |

**教训**:判据测错对象比没有判据更危险 —— 它会让"没解决问题"看起来像"通过"。
本实验里 v2 的错判差点让路线 5 的收益被埋没。

### 3.1 路线 1 实测的关键发现

路线 1(受管 History 类)实现完整后实测 **fail**,且失败原因是**方案的固有缺陷**
而非实现问题 —— 这为之前"写入时修有先天缺陷"的推断提供了实测证据:

> `end_tool_batch()` 只在"循环正常走到检查点 B"时执行。批次中途抛异常 /
> Ctrl+C / 强杀 → 到不了那里 → 受管历史内部仍是半个批次 → 落库照样非法。

**写入时看不到后续**,与 `_append_user_turn` 修角色交替却漏配对**同源**。

附带发现:把逻辑收进类改变了合成文案契约,引入一处回归
(`test_history_hygiene` 角色交替测试),修法是用回 `INTERRUPT_CLOSE_TEXT`。
说明"收口进类"并非零成本——它还牵动既有文案契约。

**方法论提醒**:路线 1 的第一次实现有 4 处接线 bug(裸 `append` 未收口),
当时结果是 4 红。必须**先把接线的 bug 修完**才能得到"方案本身行不行"的结论;
否则测的是"我没接完",不是方案。这一点在比较实验中极易自欺。

## 4. 三条路线各自的价值

### 路线 5 原子批次 —— 采纳
把"`assistant(tool_calls)` + 同批全部 tool 回复"当作**一个原子写**,批次收尾
才落库。非法状态**从未被写进磁盘**,所以不需要事后修。

- 通过硬标准(停机后磁盘合法)且通过软标准(每一次落库快照都合法)
- **不依赖任何收尾动作**:kill -9 / 断电 / 任务管理器结束进程都不影响
- 改动最小:删一处落库、加一处落库

### 路线 2 投影器 —— 采纳为互补件
`project_messages()` 纯函数保证"发出去的 messages 永远合法"。

- 它**修不了** AR-stop1(没碰落库时机),所以不是替代方案
- 但它的价值独立成立:把发送侧不变量收在**一个函数**里,并可**删掉两处保险丝**
  (实测零回归)——兜底点 7→5
- 与项目已有三单点同构:`_parse_tool_arguments` / `_make_confirm` / `_append_user_turn`

### 路线 3 单点收口 —— 封存
`chat()` 的 `finally` 统一收口。通过硬标准但**不通过软标准**。

- 它是"事后修"的天花板:修得足够及时,用户可见行为与路线 5 等价
- 但依赖"进程能走到 finally";强杀时磁盘上留着半个批次
- 按用户定的口径(**软标准通过加分、不通过也可采纳**),它可采纳但不如路线 5
- 保留为对照证据:它证明了"收口类方案到不了落库侧"

## 5. 未采纳的方向及理由(实测 + 论证)

| 方向 | 结论 | 依据 |
|---|---|---|
| **受管 History 类**(路线 1) | ❌ **实测 fail** | `end_tool_batch()` 到不了"批次中途停机"的场景 → 写时看不到后续 |
| **落库不变式**(save 前校验) | 未实现,论证不采纳 | 破坏"持久层忠实读取"对称性;每次落库全量校验成本高 |
| **快照回滚**(Hermes 做法) | 未实现,论证不采纳 | 过重:dummy 只需保证历史合法,不需回滚副作用 |
| **事件溯源**(append-only + 投影) | 未实现,论证不采纳 | 与路线 2 高度重叠,重构代价大得多 |

**说明**:上表后三行是**论证而非实测**,与路线 1(实测 fail)的证据强度不同。
按"宁要实测不要推演"的原则,它们若将来成为候选,应先做最小实测再定。

## 6. 最终决策(2026-09-16):采纳路线 3

```
路线 3(单点收口)  ← 采纳,已合入 main(ee06936)
```

**决策依据(实测,非推演)**:

两者都满足硬标准(AR-stop 全绿,停机后磁盘历史合法),但进一步实测发现
**SOFT1 与"Ctrl+C 保住已完成工具结果"是互斥的**:

| | Ctrl+C 时已完成的工具结果 | 磁盘上是否短暂存在半个批次 |
|---|---|---|
| **路线 3**(每条结果后落库) | ✅ **保住**(实测 2 条 tool 结果留在磁盘) | ❌ 存在(SOFT1 不通过) |
| **路线 5**(批次原子落库) | ❌ 整批全丢 | ✅ 从不出现(SOFT1 通过) |

**用户判定**:Ctrl+C 是**高频操作**(整个交互设计围绕它与 `/p`),且工具
可能**不可重复**(构建/网络/硬件操作),"重跑一次"不成立 → 丢结果是真实损失。
而"磁盘上短暂存在半个批次"**不是问题**,因为唯一的读取入口
`resume_session()` 会修复它 —— **实测 7/7 种半个批次形态,resume 后全部合法**:

```
P1 一批两个,一个都没回          ✓
P2 一批两个,只回第一个          ✓
P3 一批三个,回前两个            ✓
P4 悬空后又接了 user            ✓
P5 悬空后又接了多轮对话          ✓
P6 尾部是裸 tool(无主)          ✓
P7 多批:第一批发完,第二批悬空    ✓
```

**结论**:SOFT1 降级为"可选加固项";为它牺牲 Ctrl+C 的数据保留**不划算**。

### 6.1 一条被这次实验纠正的判断

我（助理）最初主张路线 5,理由是"路线 3 依赖进程能走到 finally,而路线 5
不依赖任何假设"。**这个权衡算错了**:

- 它拿**罕见事件**(强杀/断电)的收益,去换**高频场景**(Ctrl+C)的损失
- 而且"重跑一次就好"的前提**不成立** —— 工具未必幂等

**教训**:权衡时要比"频率 × 单次代价",不能只比"哪种更优雅"。
