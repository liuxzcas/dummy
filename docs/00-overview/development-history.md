## 一句话概括

**dummy 从"一个会调工具的 LLM 循环"，走成了"一个把判断权还给模型的框架"。**

这条路不是一次设计出来的，是被三次实测数据逼出来的：

```
第一次(08-25)  自我改进闭环上线后,发现模型被护栏劫持 —— 66 次调用/4 次驳回
第二次(09-16)  把护栏和验证门全部退成"只报告" —— 这是全项目的转折点
第三次(09-17++) 跨平台暴露的一堆实现缺陷(超时/编码/依赖) —— 都是"机制不完整"
```

## 阶段 0：原型期（07-24 ~ 07-25）

**目标**：跑通"问 → 模型要工具 → 执行 → 结果回喂 → 再问"的循环。

**产出**：
- `core.py` 主循环、`llm.py`（DeepSeek 兼容 OpenAI SDK）
- 5 个工具：`terminal` / `read_file` / `write_file` / `web_search` / `web_extract`
- `tools/` 注册表模式（即插即用）

**当时的判断**：
> 先不做记忆、不做安全、不做压缩 —— **只要循环能跑通**。

**文档**：`00-overview/design-phase0.html`

## 阶段 1：工具加固期（07-25 ~ 07-27）

**触发**：模型生成的工具参数**经常不合法**（JSON 语法错、编码乱、路径写法不对）。

**做了什么**：

| 改动 | 为什么 |
|---|---|
| dispatch 层加固 | 参数错误不能直接崩 |
| JSON 容错解析 | LLM 生成的 JSON 常有单引号/尾逗号 |
| 编码修复 | Windows GBK 环境下输出乱码 |
| **terminal 执行前确认** | 模型能跑任意命令 → 必须有人把关 |

**这一阶段定下的模式**：**"执行确认"是人机边界的第一次划定** —— 后来所有安全设计都从这里长出来。

**文档**：无独立文档（改动记在提交里）

## 阶段 2：记忆与压缩期（07-28 ~ 08-13）

**问题**：对话一长就超上下文；换个会话就"失忆"。

**三个大件**：

### 2.1 会话持久化（07-28 ~ 08-05）
- `.env` 加载、对话日志、`session.db`（SQLite）
- **踩坑**：时间显示是 UTC（要本地化）、多进程同 session 双开导致历史交错

### 2.2 Context 压缩（08-05 ~ 08-10）—— **本项目第一个"有设计文档"的功能**

```
方法:L1 折叠(工具结果原文归档) + L2 增量摘要
理由:先把原文留档,摘要丢了还能找回
产出:compressor.py + 质量门脚本 + 冒烟脚本 + 28 项验证
```

**当时的严谨程度**：写了 `phase2.2_plan.md`（21498 字节），**先写计划再实施**；每个 Step 有验证记录。

**教训（已记录）**：单轮 chat 里的长工具循环**不触发 L2** —— 这是已知特性，不是 bug。

### 2.3 FTS5 全文搜索（08-11）
- 双表方案（原文表 + 索引表）
- `/search` 命令

### 2.4 跨 Session 记忆（08-12 ~ 08-13）—— **第一次真正的方案对照**

```
方案 A(按需注入)  :T5 回归集 19/30 = 63%
方案 hermes-memory-v3(全量常驻 + 写入时蒸馏):26/30 = 87%
再加"历史 FTS 兜底通道"              :28/30 = 93%  ← 采纳
```

**这一阶段定下的方法论**：**同一测试集上跑不同方案，用数字说话**（后来所有架构选择都沿用）。

**文档**：`02-phase2-memory/`（7 份）

## 阶段 3：自主学习期（08-13 ~ 08-25）

**目标**：让它"越用越好"。

**三个机制**（对应三个 Step）：

| Step | 机制 | 做法 |
|---|---|---|
| **1** | **技能系统** | `SKILL.md` + 索引注入 + `/skills`；按需加载，不常驻 |
| **2** | **技能创建** | `create-skill` 元技能 + 校验 |
| **3** | **错误学习** | 教训生成 + **按需检索注入**（不常驻，避免污染上下文）|
| **4** | **自我改进闭环** | 检测 → 提案 → **人工批准** → 修改 → 验证 → **自动回退** |

**期间的关键决策**（记录在 `phase3-research.md`）：

```
D3 = C(先 A 后 B)    技能先原子、后编排
D4 = A               教训存独立库,不塞进主记忆
D5 = B(修正后)       原子技能 + 编排
```

**同期还做了**：
- 消息前缀着色（`colors.py`）
- 会话 token 用量统计（输入/输出/**缓存**/成本/窗口）
- terminal 改用 git-bash（**修复了"cmd 语法返工浪费 token"**）
- **workspace 机制**（注入当前工作目录，让 LLM 不再猜路径基准）

**这一阶段的验证纪律**：每个 Step 都有**独立验证报告**（见 `03-phase3-learning/phase3-step1-verification.md`、`phase3-step2-verification.md`、`phase3-step4-manual-test.md`），含方法论 + 过程 + 结果。

**文档**：`03-phase3-learning/`（4 份）

## 阶段 4：架构反转期（09-03 ~ 09-16）★ **全项目最重要的一段**

### 起点：09-03 ~ 09-15 的加固

```
09-03  会话占用锁(多进程防双开)
09-12  tool_calls 配对自愈(修 400 "insufficient tool messages")
09-15  P1a 工具循环护栏(相同调用反复失败 / 只读无进展)
09-15  P1b 收尾前验证门(档 A)
09-15  P2a 轮次上限可配置 + 收尾剥工具
09-15  P2b 历史卫生(尾部悬空块 / 中断序列闭合)
09-15  跨组件冲突审计 —— 修掉 4 处互相矛盾的设计
```

### 转折：09-16 一天之内连续推翻了两次

**事件经过**：

```
① 先做"验证门"(P1b):模型说完成 → 门检查"有没有跑过验证" → 没有就驳回
   同一天还做了"护栏"(P1a):同一调用反复失败 → 拦截

② 实测发现:模型被这两个机制劫持 ——
   · 一次任务 66 次工具调用,其中 4 次被驳回
   · 模型"原地打转"(想绕过护栏)
   · 更糟:护栏记的是"连续 N 次",跨轮累计 → 用户正常操作也被拦

③ 用户指正了方向:判断"是否在原地打转"是【语义判断】,该归模型

④ 当天连续三次退化:
   verify_stop.py(346 行,判决者) → 删掉,零消费者
   护栏 硬停 → 软暂停 → **纯观察者**(零拦截)
```

**这个转折的本质**：

```
改之前:代码替模型做语义判断("你在打转,不许跑")
改之后:代码只陈述事实("你连续 3 次执行了同一个调用,结果相同"),
       判断权交回模型
```

**同时期其他修复**（都是同类问题）：

| 修复 | 问题 |
|---|---|
| 成本计算把缓存算了两遍 | **高估 5.59 倍** |
| system prompt 每轮改写 | 打碎 prompt 缓存前缀（**变一字节，其后全部按未命中计费**） |
| 历史层架构选型 | **四路并行对照实验**，最终采纳"单点收口"（`chat()` 的 finally） |
| `is_tool_error` 双向误判 | 成功当失败、取消当成功 |

**这一阶段最有价值的产出**：

```
docs/00-overview/design.html  §2「判断的归属:哪些给代码,哪些给模型」

  协议合法性  → 代码硬保证(不合法请求 API 会 400)
  安全确认    → 人
  语义判断    → 模型
```

**文档**：`04-hardening/`、`91-experiences/verification-gate-rollback-star.md`（STAR 复盘）

## 阶段 5：跨平台与输出层（09-17 ~ 10-14）

**背景**：用户要部署到 Ubuntu（且强调"我不可能只在一台机器上用"）。

### 5.1 输出层收口（09-17）

```
问题:116 处散落的 print(),没有"输出层"概念
解法:ui.py —— 把"拼消息"(build)与"打印"(emit)分开
理由(用户原话):"未来 GUI 不一定适用 print(),到时只改'打印'部分"
产出:PlainRenderer / LineRenderer / SilentRenderer
```

### 5.2 `env_probe`：探测而非设置（09-16 ~ 09-17）

```
原则:不写死环境假设 —— 探测后如实声明,绝不 mutate 环境
产出:返回首行 [SHELL: git-bash | os=win32 | console=cp936 | py_io=utf-8 | fs=utf-8]
```

### 5.3 平台约定技能表 + 换行符报告（09-17）

```
问题:模型写完文件总爱再跑 sed 转换换行符(不知道 write_file 已写 CRLF)
解法:返回值报告实际换行符 [换行 CRLF] → 消除多余的 sed
```

### 5.4 一连串"实现缺陷"修复（09-18 ~ 10-14）

| 问题 | 根因 | 性质 |
|---|---|---|
| terminal 卡死、不超时、无日志 | `subprocess.run(timeout=)` 只杀直接子进程 | **机制不完整** |
| 中文输入退格留残影 | 全项目没 `import readline` | **机制不完整** |
| 依赖崩溃 `process() takes no keyword arguments` | 只锁下界 → 装到 openai 3.x → httpx2 有 bug | **依赖管理缺陷** |
| 异常被吞、看不到 traceback | 注释说"显示 traceback"但**没调用** | **实现与描述不符** |

**这一阶段的关键区分**（用户明确要求）:

```
设计错误(如护栏) → 要推翻重来
实现缺陷(如超时) → 补上就行
两者不能混说
```

**文档**：`05-cross-platform/`

## 贯穿全程的几条主线

### 主线 1：判断权的边界（最重要）

```
阶段 0-3:  代码做很多判断(容错、压缩、护栏、验证门)
阶段 4:    发现"代码不该做语义判断" → 大规模退回
阶段 5:    把这条原则应用到新功能(env_probe 探测不设置、超时报告不判决)
```

### 主线 2：验证方式从"感觉对"到"实测数据"

```
阶段 2:  方案 A vs hermes-memory-v3,19/30 vs 28/30
阶段 4:  历史层四路并行对照
阶段 4:  成本 bug 靠实测发现(高估 5.59 倍)
阶段 5:  超时 bug 靠实测发现(设 5 秒实际 20.4 秒)
```

**沉淀出的信念**：**实测数据 > 设计推理**（多个 bug 在代码审查中看不出来 —— 都是"逻辑正确但前提错误"）。

### 主线 3：文档与验证的纪律

```
Phase 2.2 起:  先写 plan 再实施
Phase 3 起:    每个 Step 有独立验证报告
教训沉淀:      STAR 复盘(docs/91-experiences/)
```

### 主线 4：跨平台

```
早期:  写死 Windows 假设(git-bash 路径、cmd 回退)
阶段 4: env_probe"探测而非设置"
阶段 5: start.sh、readline 跨平台适配、依赖上界
```
