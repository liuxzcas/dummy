# 工具结果结构化 — 设计文档（草案，未实施）

状态:**待评审** | 日期:2026-09-16 | 前置:两份调研报告（见 §8）

---

## 1. 为什么做这件事

### 1.1 触发事件（真实 bug）

2026-09-16 实测 `lessons.is_tool_error`，发现它**两个方向都错**：

```
成功当失败:  terminal 每条结果都附 "[EXIT CODE: N]"(成功是 0)，
             而判据表里是 "[EXIT CODE: " 字面量
             → 成功的命令被判失败（6 个成功样例里 2 个全部中招）
取消当成功:  5 种"用户取消/拒绝"文案不含任何标记 → 被判成功
             → "取消的 pytest"能当"通过证据"
```

**已修**（`3537789`）。但修法是**继续猜字符串**——只是把规则写得更准。
**本文档要讨论的是**：要不要消除"猜"这件事本身。

### 1.2 这个 bug 不是孤例

工程调研发现**结构性同源**的案例：

- **LangChain #36411**：结构化的 `status="error"` **已经存在**，但路由逻辑没读它
  → 失败被当成功
- **Aider #2167**：formatter 改动代码时返回非零退出码 → 被误认为"有 lint 错误"

**共同点**：判定逻辑与"事实来源"之间隔着一层**需要猜测的表示**。

### 1.3 钉死问题陈述

> **框里没有任何一处"说了算"的成功/失败来源。**
> 每个工具用自己的一套文案表达成败（`[错误]` / `[EXIT CODE: N]` / `[用户取消]`...），
> 而所有消费方都在**猜这些文案**。

消费方共 **5 处**（全部依赖 `is_tool_error` 这一个猜测函数）：

| 消费方 | 位置 | 猜错会怎样 |
|---|---|---|
| 教训生成 | `core.py:1094` | 成功的命令触发一次旁路 LLM 反思（烧 token + 噪音教训） |
| 工具护栏计数 | `tool_guardrails.py:248` | 成功命令计入 `exact_failure` → 同命令同输出 6 次被硬拦 |
| 验证门写入判据 | `verify_stop.py:104` | 写入成败误判 |
| 验证门证据判据 | `verify_stop.py:197` | 证据误判（已单独打补丁，因只有它需要 `[SHELL:`） |
| dispatch 出口 | `tools/registry.py:253` | 错误率统计失真 |

## 2. 调研结论（决定方案形态）

### 2.1 生态的答案是"**双层并存**"，不是二选一

| 项目 | 做法 | 判定逻辑读什么 |
|---|---|---|
| **Anthropic** | wire 协议 `tool_result` 有 `is_error: bool`（唯一协议级结构化的） | 字段 |
| **MCP** | `CallToolResult.isError` + `structuredContent` | 字段 |
| **OpenHands** | `Observation.is_error` + `TerminalObservation.exit_code`；**同时**在文本里追加 `[Command finished with exit code N]` | **`exit_code == 0`**（与文本解耦） |
| **Aider** | `run_cmd()` 返回 `(exit_code, output)` **元组**，物理分离 | 元组第一个元素 |
| **LangChain** | `ToolMessage.status: Literal["success","error"]`（注释明说**不发给模型**） | 字段 |
| **OpenAI 规范** | tool content 是纯字符串，**协议层没有 status 字段** | —— 全生态困境的根源 |

**关键**：**没有项目走结构化后退回文本**。真实演进是"纯文本 → 结构化，**保留文本并叠加结构化**"。

MCP 的 `schema.ts:763-766` 官方注释给出了最权威的设计依据：

> "必须用**结果内字段**而非协议级错误，否则 LLM 看不到错误、无法自我纠正。"

### 2.2 学术侧：结构化有用，但**理由和直觉不同**（重要）

**最相关的论文**：arXiv 2607.14167《Structured Feedback Improves Repair in an LLM Agent Loop》
（配对实验：50 合成游戏 × 4 策略 × 2 模型，2,652 次 LLM 调用）

| 发现 | 对我们的意义 |
|---|---|
| 反馈含 `location + observed + expected` → 比 raw 报错 **+42~44pp** | 支持"错误信息要带**正确做法**" |
| **消融：增益全部来自 `expected` 字段** | ⭐ 结构化字段本身不是收益来源 |
| **JSON 键值 vs 自然语言散文：差 0–2pp** | ❌ **推翻**"改成 JSON 能让模型更懂" |
| "只有 location + observed、无 expected" ≈ 基线 | ⚠️ **半套结构化没有效果** |
| 纯重试无增益（预算 4→8） | 支持"失败要分类，不能一律重试" |

**强证据反对子串匹配**：`substring heuristic` 与人类标注一致度 **κ=0.049**（等同抛硬币）。
这条直接支持"消除猜测"。

### 2.3 反例研究：四类失败模式，都有实验数据

| 失败模式 | 论文 | 数据 |
|---|---|---|
| **把成功当失败** | When Tools Fail (2406.19228, CMU/EMNLP 2024) | 故障数为 0 时模型误判率极高 ← **正是我们刚修的 bug** |
| **把失败当成功** | Agents Trust Tools Too Much (2609.05587) | Code Executor override **39.1%**；仅 1.8% 告知用户。**工具通道自带权威性**（同一数字由 User 给出时 override 仅 0.2%） |
| **重试循环** | ToolMaze (2606.05806) | futile trial-and-error；PRR 跌 **37%** |
| **错误归因** | AgentProp-Bench (2604.16706) | 拒绝能力与恢复能力**统计独立**（ρ=0.041）；伪造工具执行高达 **37.5%** |

### 2.4 文献空白（诚实标注）

**没有找到专门研究"agent 如何理解 Unix 退出码"的论文。**
最接近的是 ToolMaze 的 `explicit/implicit × transient/permanent` 2×2 分类。
SHIELDA 把 `Tool Invocation Exception` 一律映射到 `Retry with Backoff` —— **是错误示范**
（`grep` 无匹配返回 1 会被无意义重试）。

**这条空白意味着 §3.3 的"退出码语义"设计只能靠工程判断，没有学术背书。**

## 3. 设计

### 3.1 核心原则（三条，按重要度）

**原则 1：判定逻辑永不读文本。**

```
结构化字段 → 供控制流 / 遥测 / UI 判定   ← 唯一的判定来源
文本内容   → 供 LLM 阅读                ← 永远不参与判定
```

**原则 2：文本原样保留。**

不是"用结构化替代文本"，而是**叠加**。理由：现有工具输出是给模型看的、已调优的；
换掉它会损失信息（OpenHands 就是两层都留）。

**原则 3：`is_error` 与 `exit_code` 语义独立。**

**非零退出码 ≠ 失败**。这是 Aider #2167 的教训。至少要区分：

| 类别 | 例子 | 该不该算失败 |
|---|---|---|
| 正常无结果 | `grep` 无匹配（exit 1）、`diff` 有差异（exit 1） | ❌ 不算失败 |
| 真失败 | 命令不存在（127）、语法错误（2） | ✅ 失败 |
| 未执行 | 用户取消 | ⚠️ 不算失败，但**不能算成功** |

### 3.2 字段定义（最小集）

```python
@dataclass
class ToolResult:
    content: str                    # 给 LLM 看的文本（原样保留）
    is_error: bool                  # 控制流判定用 —— 唯一判定来源
    error_kind: str | None = None   # 分类（见 §3.4）
    # --- 可选:仅 terminal 有 ---
    exit_code: int | None = None
```

**为什么字段这么少**：调研显示字段**不是**收益来源（§2.2）。
最小集只解决"判定不靠猜"这一个目标；不为了"看起来结构化"堆字段。

**明确不做**：把 `content` 改成 JSON（无证据支持，§2.2）。

### 3.3 `error_kind` 分类（对齐 ToolMaze 的 2×2）

| kind | 含义 | 典型来源 | 建议动作 |
|---|---|---|---|
| `none` | 成功 | —— | 继续 |
| `not_executed` | 用户取消/拒绝，**没跑** | `[用户取消]` | 不算失败；不能当证据 |
| `empty_result` | 跑了，但"无结果"是正常语义 | `grep` 无匹配 | **不算失败** |
| `transient` | 暂时性（超时/网络） | timeout | 可重试（带退避） |
| `permanent` | 确定性失败（命令不存在/语法错/参数错） | exit 127 | **不要原样重试** |

**⚠️ 诚实标注**：`empty_result` 的识别**需要每个工具自己声明**（只有工具知道
"exit 1 在这里是正常的"）。这是本设计里**最重的一块**，也是唯一没有学术背书的判断。

### 3.4 改动清单（按调研建议 4：加字段后审计所有控制流分支）

| # | 位置 | 改动 |
|---|---|---|
| 1 | `tools/*.py`（5 个工具） | 返回 `ToolResult` 而非 `str` |
| 2 | `tools/registry.py:253` | 读 `is_error`，不再调 `is_tool_error` |
| 3 | `core.py:1094` | 读 `is_error` |
| 4 | `tool_guardrails.py:248` | 读 `is_error` |
| 5 | `verify_stop.py:104` / `:197` | 读 `is_error`（可删掉 `[SHELL:` 那个补丁） |
| 6 | `lessons.py` | `is_tool_error` 降级为**兼容层**或删除 |

**⚠️ 风险点（LangChain #36411 的教训）**：第 2~5 项是**独立的控制流分支**，
必须逐个审计，不能只改"主路径"。**建议先做一次全面 grep 列出所有消费方，
再逐个改**（本次已列出 5 处，但改的时候要再确认）。

### 3.5 迁移与回退

**迁移**：分两步，每步可独立验证

1. **加字段**（不改消费方）：工具返回带上 `is_error`，但没人读它
   → 验证：全量测试通过，行为无变化
2. **切消费方**（逐个）：每改一处跑一次全量测试
   → 验证：并行为比对新旧判定（见 §4）

**回退**：`is_tool_error` 保留为"从文本推断"的兼容实现。
若新方案出问题，消费方切回旧函数即可 —— **单点回退，不需要动工具**。

### 3.6 与现有机制的关系

| 现有机制 | 结构化后 |
|---|---|
| `verify_stop` 的 `[SHELL:` 补丁 | **可删**（`not_executed` 显式表达，不用猜） |
| `tool_guardrails` 的"报错内容相同才算累计" | **保留**（那是"同一次失败"的判定，与成败判定正交） |
| 护栏的"失败内容也相同"要求 | 保留 —— 它是**防误拦**的，不是成败判据 |

## 4. 验证方案

### 4.1 必做：旧新判定并行的对照

在切消费方之前，**先让两套判定同时跑**，记录不一致：

```python
# 临时埋点（验证后删除）
new = result.is_error
old = is_tool_error(result.content)
if new != old:
    log(f"判定分歧: {tool} new={new} old={old}")
```

**为什么必须做**：LangChain #36411 的教训是"字段加了但没人读"。
**并行对照能同时发现**"字段值错"和"消费方没切"两类问题。

### 4.2 测试清单

| 测试 | 断言 |
|---|---|
| 各工具成功 → `is_error=False` | 5 个工具 × 典型输出 |
| 各工具失败 → `is_error=True` | 含 exit 127 / 语法错 |
| 取消 → `is_error=True` 且 `kind=not_executed` | 不能当成功 |
| **`grep` 无匹配 → `is_error=False`** | ⭐ 回归 Aider #2167 那类坑 |
| 消费方全部读字段 | grep 确认无残留 `is_tool_error` 调用 |

## 5. 不做的事（明确排除）

| 不做 | 理由 |
|---|---|
| 把 `content` 改成 JSON | 调研明确否定（JSON vs 散文差 0–2pp） |
| 堆大量字段 | 字段不是收益来源；最小集只解决"判定不靠猜" |
| 在错误信息里加 `expected` | **有价值**（+42~44pp），但属于**第二阶段**，且需要每个工具知道"正确做法"，成本高。**本文档不含** |
| 改协议层（tool 消息格式） | OpenAI 规范没有 status 字段，改不了 |

## 6. 收益 / 代价（供决策）

**收益**
- 根治"猜字符串"类 bug（含刚修的这两个方向）
- 消除 5 处消费方的误判风险
- 可断言、可日志、可 trace 评测（调研里"选 JSON 的正当理由是程序侧"）
- 可删掉 `verify_stop` 的 `[SHELL:` 补丁

**代价**
- 改 5 个工具 + 5 处消费方，**触及工具循环的所有路径**（回归风险中高）
- `empty_result` 需要每个工具声明"我的退出码语义"——**最重的一块**
- 与压缩器/历史层无交互（结果对象在 `content` 上仍是字符串），风险可控

**我的倾向**：**值得做，但应作为独立阶段**（像历史层那样：先方案 → 试验 → 对照 → 采纳），
不建议顺手改。理由是它触及工具循环所有路径，而 `empty_result` 那块的复杂度
取决于"要支持多少种工具的语义"——**这个范围应该先划清**。
